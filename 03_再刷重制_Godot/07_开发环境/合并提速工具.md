# 合并提速工具

本工具按交接板 2026-10-16 的沙僧协助计划制作。只改变开发流程，不改变游戏规则；交叉核查与人工进度估计继续由原工作者负责。

## 同步正式西游：自动识别新增用例

`python3 03_再刷重制_Godot/03_转换工具/同步正式西游.py --accept-additions`

仍先备份、转换、运行全部参照探针并核对来源。识别已知参照的稳定用例键：事件 id、敌群/交礼、伤害双方与技能、AI 场景与角色、商店商品与状态等；同键重复项按多重集逐条比较。旧用例必须全部完全相同，只允许新增键。新地图还检查通行度矩阵结构。

- 不带参数也会报告“只增新用例”，退出 2，留给人工核对；带参数且同源验证通过才自动接受并登记，退出 0。
- 只有正式版本与运行脚本完全相同、旧输入 SHA 全部原样保留才允许自动接受；新增切片输入可以增加。
- 旧用例改变/删除、同键追加、未知结构变化、新用例报错或不结束、来源校验失败，一律不自动接受。
- 来源身份只忽略顶层字段；用例中的 source 等测量内容不会被忽略。
- worktree 继续自动不登记；`--no-register` 也保持有效。完整比对在备份目录的同步报告.json 中，不只打印摘要。

## 合并车道：准备与收尾

在 main 使用工具，任务名对应现有的 `claude/<任务>` 或 `codex/<任务>` 工作树；主工作区与车道均须干净，交付单标为“可合并”。

1. `03_再刷重制_Godot/07_开发环境/合并车道.sh <任务> --dry-run`：只读计划，不建状态文件、不合并、不清理。
2. `03_再刷重制_Godot/07_开发环境/合并车道.sh <任务>`：正常 merge --no-ff；切片/转换器/参照探针有改动才同步并导入；游戏内容有改动才递增开发编号；把交付单草稿并入变更记录，替换草稿及车道修改文件里的编号占位，删除交付单。仅测试、文档与工具不递增游戏编号。替换文件范围在准备计划中列出，排除 AGENTS.md 与交付模板；其它车道、main 的无关文件不扫描替换。
3. **唐僧手改交接板和进度账**：移除活动车道，加入待交叉核查（写车道分支或提交号），按实际范围更新完成度。改动先保留未提交。
4. `03_再刷重制_Godot/07_开发环境/合并车道.sh <任务> --finish`：核对登记、原始加权合计与预期文件范围，先只暂存本批交付单的删除，使检查使用的 Git 文件清单同步；运行完整检查和 oracle；提交收尾，再调用既有工作树清理保护。**车道交付后继续工作也能合并**：车道常在同一工作树换新分支接着做（会话绑在这个路径上），只要交付提交已并入 main，工作树不在交付提交、换了分支或有未提交改动都不拦，只跳过这条工作树的清理并提示；交付分支已不是该工作树的当前分支就照删（`git branch -d`，有未并入的提交时保留）。准备合并时就已经没有工作树停在交付分支上的，按分支引用 `claude/<任务>` 合并（交付单等从交付提交里读，带切片改动时不取车道产物、直接在 main 完整同步），新分支上的提交不会带进来。默认执行者 Claude（唐僧）；额度接力时两步均加 `--executor Codex`。
5. **推送 GitHub**（用户 2026-10-18 定：每次合并后推 main）：收尾全部完成后，若主工作区有名为 `github` 的远端，先 `ls-remote`／`fetch` 它的 main。GitHub 上有本地 main 没有的提交时，列出这些提交并跳过推送，从不强推，由唐僧人工核对；否则 `git push github main`。远端不通、认证失败或超时（120 秒）只打印一行警告，合并照样算完成，下次合并的推送会把缺的提交一起补上。没有 `github` 远端就跳过。云端分支一律由唐僧在 Mac 上像车道一样合并，不用 GitHub 的合并按钮，Mac main 仍是唯一原件。

编号替换前保存原文与替换结果的 SHA；中断后允许从两种已知状态接续，不重复编号。收尾前后都核对非共用文件只有计划中的替换：若界面风格等文件还有人工编辑，保留改动并停止，即使已手动暂存也不会顺带提交。检查失败时，交付单删除可能已暂存，其余工作现场仍保留，修正后可继续 --finish。

交付后若另一个车道先合并 main，仍可正常合并；有冲突就停止保留。**冲突接续**：唐僧解决后 `git add`，再运行同一条准备命令，工具按规范（带执行者／核查行）提交合并并往下做；改为放弃时 `git merge --abort`，车道 `git merge main` 解决后重新交付，再运行即按车道新提交与 main 现状重新计划（尚未合入时都会重新计划）。**一批合并只检查一次**：几条车道同时可合时，前几条收尾用 `--finish --batch`，照常核对交接板、暂存、提交「合并 <分支>（dev.NNN）收尾」，但不跑 `检查.sh`、不清理工作树、不推送，登记在 `.git/lane-merge/batch.json`；准备下一条时会提示本批已攒几条。最后一条用普通 `--finish`：跑一次 `检查.sh --oracle`，通过后提交，再逐条清理本批车道（已在同一工作树继续工作的只跳过它的工作树，规则同上），最后推送。最后的检查失败时什么都不清理、不推送，并列出本批每条车道的合并提交与改动文件，对照失败项定位（在嫌疑车道工作树单独跑失败的场景）。检查本身的问题修好后重跑同一命令接续；要撤出一条用 `--abort-batch`（不带任务名）：拒绝未跟踪文件、进行中的冲突和已推送的批；先 `update-ref refs/lane-merge/aborted-<时间>` 记下当前 HEAD，未提交改动用 `git stash create` 存成 `…-wip`（不碰共用 stash 栈），再 `reset --hard` 到本批第一条合并前的 main，删掉批清单与状态文件，各车道工作树原样保留；之后重新合没问题的车道。不用 revert 撤：撤掉的合并以后再合会带不回原改动。**多张交付单**：分支带来的其它交付单标了可合并的，草稿按文件名顺序接在主交付单后一并并入、删除；没标的只提示，唐僧在 main 删掉后 `--finish --also <路径>`。`--also`（可重复）也用于合并时顺带改的规则等文件。草稿里按交付目录口径写的相对链接，并入时自动改成变更记录口径。草稿只有整行「待写」「（待写）」才算未完成。工具不自动解决冲突、不重置、不删除失败现场、不顺带暂存其他文件。状态在 `.git/lane-merge/state.json`，重复准备不会重复追加草稿或递增编号；失败可查看状态后接续。main 或车道 HEAD 被预期外改变时先人工核对。执行中的同类工具用互斥锁串行；若进程被强行终止留下 running.lock，确认旧进程已结束再人工移除该锁。

## 测量变化接受与批量收口（期七，2026-10-26 哪吒）

- **同步拒收后接着合**：准备阶段的同步因测量改变退出 2 时，工具打印两条命令：先 `python3 03_再刷重制_Godot/03_转换工具/生成接受单.py --out 04_验证/测量接受/<分支>.json --reason-from <交付单>`（按最新同步报告的 `changeCandidates` 生成接受单草稿；`--reason "理由"` 给全部条目同一句，都不给就留空，打开逐条核对、补理由，理由不足 4 字的同步不认），再 `合并车道.sh <任务> --accept-changes <接受单>`：把接受单记进本次合并状态（不用手改 `.git/lane-merge/state.json`）并接着同步；接受单是 main 上新写的就记进 `also`，收尾时一并提交。只在还没同步完时有效，`--finish`／`--dry-run` 不配。草稿只是照抄，同步仍逐条核对摘要与字段、每条都要用上。
- **`--close-batch`**（不带任务名）：本批都 `--finish --batch` 收尾、没有新车道要合时统一收口：跑一次 `检查.sh --oracle`（加 `--affected` 时以本批第一条合并前的 main 为基准），通过后逐条清理本批工作树（规则同 `--finish`）、删 `batch.json`、推送；失败照批末失败一样列出各条车道带进来的改动，什么都不清理、不推送，修好重跑同一命令。还有车道在合并中（`state.json` 在）或 main 有未提交改动时拒绝。
- 合并工具判断 main 改动范围时逐个列未跟踪文件（`git status -uall`），新目录里的允许文件不会被当成整个目录拦下。

## 选测：按改动只跑相关部分（三级检查②）

- `检查.sh --affected <基准提交>`：`选测.py` 取「基准到工作区」的改动（含未提交与未跟踪文件），按 [选测对照.json](选测对照.json) 自上而下第一条匹配的规则归组，各组选中的 Godot 场景与非 Godot 检查取并集；先打印每个文件归哪组、选了什么，再只跑选中的部分。文档与登记检查（JSON、链接、开发编号、交付单与占位）照常跑。不加 `--affected` 时行为与原来完全相同。
- 分组：只改文档／登记 → 只跑文档与登记检查；合并递增的开发编号（`project.godot`、`build_info.json` 只改版本行）同此，改了别的行就整轮；界面（`modes/xiyou/ui/`、`core/`、`scenes/`、`ui_reference/`）→ 引用它的测试（按文件名与 `class_name` 在 `tests/` 里找，一个也没有就跑 `ui_smoke`）＋`xiyou_event_compare`；战斗核心（battler、damage、state_effects、actor、enemy、battle_logic）→ 再加 `xiyou_rules` 全部段、共性参照与内容覆盖、同源检查；切片、转换器、oracle 探针、测量接受单 → 同战斗核心再加工具回归；地图解释器（`map/`）→ 事件对照＋楼层与地图专项；其它游戏模块（`modes/xiyou/core/`、`battle/` 其余文件）→ 引用它的专项＋事件对照；改了测试 → 跑那个测试（辅助脚本跑用它的场景，如 `xiyou_rules.gd` → 全部段）；夹具 → 引用它的测试，没人引用就整轮；开发工具 → 工具回归；**对照表里没有的路径一律整轮**（整轮时与不加 `--affected` 相同，仍沿用上轮通过结果）；选中了全部场景时也按整轮跑。已删除的测试或夹具没有测试再引用时不选场景。
- 同源检查要 `--oracle`；选中了却没加会打印警告。改对照表只改 JSON，`测试选测.py` 校验最后一条必须是 `*` → 整轮。
- 回看某次合并会选什么：`python3 03_再刷重制_Godot/07_开发环境/选测.py <合并>^1 --head <合并>`（只读）。
- `合并车道.sh <任务> --finish --affected`：用本次合并前的 main（攒批时取本批第一条合并前的 main，覆盖整批）作基准跑 `检查.sh --oracle --affected <基准>`，通过后照常提交、清理（能清就清）、推送；收尾提交加尾注「验证: 选测（基准 …）」。`--affected` 不和 `--batch` 同用，`--batch` 语义不变。
- **选测已验**：选测通过的合并在当天的全量检查之前算「选测已验」；全量照旧是不加 `--affected` 的 `检查.sh --oracle`（或 `--finish`），每天一次，阶段审查前一次。

## xiyou_rules 按编号过滤（车道只比新增部分）

`RULES_ONLY_TROOPS=833,834 RULES_ONLY_ACTORS=178 python3 03_再刷重制_Godot/07_开发环境/并行测试.py <godot> <工程> xiyou_rules.tscn xiyou_rules_d2.tscn …`：只比这些敌群的敌人能力值、这些角色的能力值和涉及它们的伤害行（逗号或空格分隔）；两个都不设时行为不变。过滤时不分份，每个难度的第 0 份（`xiyou_rules`、`xiyou_rules_d2`～`_d6`）管全部选中的行，其它份只记一项「由第 0 份覆盖」，所以只跑 6 个第 0 份就够；每个难度另断言至少选中一行，编号写错会失败。比对逻辑、第 0 份的同源与过期参照自检不变。车道交付仍要按「三级检查」跑必跑项（难度 1 四段不过滤）；过滤只用于过程中快速验新增。`检查.sh` 在这两个变量设着时拒绝运行，免得过滤结果被记成整轮通过、下轮沿用。

## 进度账：只对总和取一次小数

- `python3 03_再刷重制_Godot/07_开发环境/进度账.py`：只读，打印原始加权和与一位小数显示值。
- 加 `--check`：核对账表合计、当前状态中的数字，不一致返回非零。
- 加 `--write`：更新各行原始“计入”、合计与当前状态；不替人评估完成度。需要更新口径时显式加 `--as-of dev.NNN`，否则保留已核口径。
