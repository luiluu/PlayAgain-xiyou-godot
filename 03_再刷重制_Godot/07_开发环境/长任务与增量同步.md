# 长任务与增量同步

`同步正式西游.py`默认先转换，再按每个探针的输入和已有产物SHA决定是否运行。首次运行或`--full`强制跑全部探针。已有`--from-worktree`克隆路径照旧按转换工具与产物指纹验证；`--full`不能与它同时使用。缓存放本工作树`03_转换工具/mv_oracle/.sandbox/incremental-cache.json`，不入Git，不混进generated产物。

缓存输入包括冻结源全部文件、Node版本与实际node_modules、Python版本与相关环境、探针与本地依赖、共享宿主、隔离起始存档目录。转换器Python文件不进键（探针不执行Python）：读转换产物的探针按转换后的manifest／db／maps内容失效，转换器改了但产物没变时不重跑。切片按字段失效：探针只写`SLICE.<字段>`时只看这些字段（如help看actors／maxLevel等，智能AI只看troops）；认不出的写法（整份传出、`SLICE[...]`）退回整份切片SHA。

最慢的三个探针再按单元分片（`incremental_sync.SHARDS`）：`smart_ai`、`slice`按敌群，`event`按地图（单元键为转换后`MapNNN.json`的SHA）与公共事件。除该字段外的输入都不变、上次产物SHA也对得上时，只用`XIYOU_PROBE_UNITS`跑新增或变了的单元，其余单元的记录由`03_转换工具/oracle_shard_merge.cjs`从上次产物按全量顺序合并，结果与全量逐字节一致；只删单元或换顺序时不跑探针只合并。`smart_ai`另用第一个敌群做行动序列，第一个敌群变了就整体重跑。改合并代码（`oracle_shard_merge.cjs`）会让分片探针整体重跑；`incremental_sync.py` 改按 `SHARD_TOOLING_REVISION` 修订号进键，只有改了单元划分／核对／合并相关逻辑才把它加一（tools-probe-deps；`XIYOU_PROBE_HELPER_DEPS=0` 回到按整份内容）。

**事件探针的分片资格按「读取面」审计（2026-10-25 哪吒）**：`event_probe.cjs` 读转换产物，只有审过「只读 maps 与 manifest.slice.commonEvents」才能按地图分片（`incremental_sync.GENERATED_SHARD_AUDITS`）。原来审的是整份文件 SHA，10-24 两次只改运行逻辑（成就弹窗 init、色调天气快照）就让审计失效，此后每次加地图都悄悄整轮重跑全部事件页（悟空一轮 3206 秒）。现在可写 `reads:<读取面 SHA 前 16 位>`：读取面只取含文件读写、转换产物路径、`require`、`SLICE`／`MANIFEST`、环境变量的行（`READ_SURFACE`），改别的逻辑不影响分片资格，改了读法才退回整轮。探针本身改了照样整体重跑一次（依赖指纹在键里），这里只决定之后能否按地图增量。审计失效时同步日志与标准输出打一行 `SHARD_OFF {"probe":…,"file":…,"reads":…}`；`测试角色同步提速.py` 断言真实 `event_probe.cjs` 仍过审计，改了读法会在那里失败并给出新值，核对后照抄进 `GENERATED_SHARD_AUDITS`。
- 真实数据比对：`python3 03_再刷重制_Godot/03_转换工具/事件增量比对.py [--units m171,m225]`，先核对 `events.json` 是当前输入下发布的产物（否则退出 3，先同步），再只跑挑出的几张地图并按同步的合并方式拼回，要求与整轮产物逐字节一致（`EVENT_INCREMENTAL_COMPARE={…"identical": true}`）。
- 强制整轮：`同步正式西游.py --full`（`--full-probes` 同义）。

**事件状态探针按地图增量＋分段（tools81 哪吒）**：`event_state_probe.cjs`（1 万多个有状态变体）原来在同步里单进程整份重量——同步开跑前删掉`.sandbox`里的上次产物，探针自带的增量（BV）从没生效，整轮两小时以上，是同步的长杆。现在：①摘要按「冻结源除`data/MapNNN.json`以外的全部＋开局设定＋探针代码」加「本例读到的那几张地图」（探针包住`fs.readFileSync`记下每例读了冻结源哪些地图：所在地图、场所移动去的、开局快照与插件自己读的）算，不再含整份切片；换源只改了几张地图、或切片只加了地图时，别的变体原样取回，1% 抽查重跑（结果和读到的地图都要相同，不同就整份重跑）。②同步里与`补跑事件状态探针.py`一样按变体序号分`XIYOU_STATE_SHARDS`段（默认 4，每段占 1 槽）并行。③上次的结果用已发布的`generated/oracle/event_states.json`，摘要记在`.sandbox/event_state_keys.json`（摘要账，按结果文件 SHA-256 认领，留最近 6 份；`新建工作树.sh --补齐`带账、已有账时合并）；账上认不出就整份重量，同步日志里那段输出开头写明是哪种。代码在`03_转换工具/event_state_shards.py`（同步与补跑共用，进该探针的缓存键）。回退：`XIYOU_STATE_SHARDS=1`单进程、`XIYOU_STATE_INCREMENTAL=0`整份重量。回归：`测试事件探针分段.py`（克隆冻结源改一张无关地图→全部取回、改变体所在地图→只它们重跑且结果一致；同步分段路径经摘要账第二轮全部取回；摘要合并与账）。

**逐单元核对（木吒 2026-10-26）**：原来分片探针只要 generated 里的产物 SHA 与缓存记的不同就整轮重跑——车道合并 main 后 `--补齐` 用主工作区的产物刷新 generated、上一轮失败作废了缓存条目、车道还没有自己的条目，都会这样（10-25 各车道同步 slice＋smart_ai 每轮 1.4～3.3 万 CPU 秒，几乎都是这个原因）。现在每次产物复制进 generated（或命中复用）时，用 `oracle_shard_merge.cjs --digest` 记下每份产物的单元摘要：每个单元（敌群／地图／公共事件）全部记录的 SHA-256，加上非分片部分（来源身份、开局设定等，分片字段位置留占位）的 SHA-256。产物 SHA 对不上时，逐单元核对：某个单元能复用，当且仅当有一条账的输入键与本次完全相同、该单元的单元键相同，且 generated 现有产物里该单元的记录与账上的摘要逐份相同；其余单元用 `XIYOU_PROBE_UNITS` 重跑，再照常合并。全部单元都对得上就只合并（不跑探针）；非分片部分对不上就至少重跑一个单元，让它取自新产物；一个都对不上就整轮。账有三处：缓存条目本身、`ledger`（随产物写入，失败或作废都不删，因为它描述的正是 generated 里现有的内容）、`carried`（`新建工作树.sh --补齐` 从主工作区带来的 ledger，车道已有缓存也照带）。所以车道合并 main、`--补齐` 之后，只要输入与 main 相同的单元都按 main 的账复用，只跑本车道改了的单元。同步日志 `CACHE_MISS` 原因里多一项 `unit-verified`（复用几个、跑几个、来自哪本账）。回归在 `测试增量同步.py` 的 ShardTests（换了记录只跑那个敌群、只改写法只合并、非分片部分变了跑一个、作废后按 ledger、按 carried、探针改了或记录全变则整轮，各自与全量逐字节相同）；真实数据抽 3 个敌群跑 smart_ai 与 slice 难度 1，合并结果与整轮产物逐字节相同（54 秒，整轮分别约 28 分钟、4～12 分钟）。改合并或缓存代码照旧让分片探针整轮重跑一次（本次也是：main 合并后第一轮同步整轮，之后车道按 carried 复用）。

**按探针实际依赖算 helper 键（tools-probe-deps 哪吒，dev.421）**：原来 `mv_oracle/` 里任一 helper 改了 96 个探针全部重跑。现在（`XIYOU_PROBE_HELPER_DEPS`，默认开，`=0` 回旧）每个探针的依赖＝从探针文件起的静态 require 图（只认字面量本地路径）∪ 字面量 `path.join(__dirname,…)` 读到的 mv_oracle 文件 ∪ 上次运行时的记录（同步给探针 `--require` 预加载 `probe_dep_recorder.cjs`，记读过／require 过的 mv_oracle 文件，写 `.sandbox/probe_deps/<探针>.<pid>.json`，记账时并成 `<探针>.json`）。认不出的写法（非字面量 require、拼路径）又没有记录时保守地带上全部 helper。旧格式缓存条目按存下的输入明细换成新键，换算法本身不触发重跑。
- 携带：`--carry-cache`（`新建工作树.sh --补齐`）把主工作区 `.sandbox/probe_deps/` 里车道没有的记录文件逐个带过去（已有的不覆盖、含符号链接拒绝）；不带的话 slice_probe／shared_system_probe／event_state_probe 这类动态读取的探针在车道里改带全部 helper，键对不上就重跑。总装 `--from-worktree` 克隆车道产物时同样把主工作区缺的记录从车道补上（同步报告 `fromWorktreeProbeDeps`）。
- 审过的 helper 改动影响面（`03_转换工具/helper_change_scope.json`，`XIYOU_HELPER_SCOPE=0` 不用）：每条 `{file, from, to, rerun, why}`，表示这份 helper 从 from（SHA-256）改到 to 只影响 rerun 里的探针，其余探针算键时把它当作还是 from（可连成链）。格式错直接报错。声明写错会让产物过期，**新增条目按甲档交叉核查**。
- 同步内占槽次序（`XIYOU_SYNC_SLOT_ORDER`，默认开）：同一同步里等槽的探针在进程内排队，一次只放第一个去抢共用槽；次序＝已有段占到过槽的探针其余段优先 → 估计耗时长的先（`.sandbox/probe_durations.json`）→ 先来先得。不抢已占的槽，不改跨工作树排队。
- 回归在 `测试增量同步.py`（依赖图、记录、携带、克隆补记录、影响面声明、开关回退、旧条目升级、槽次序）。
- **指纹的维护约定（cc 审查 2026-11-10，dev.433；审的是上面这套算法，现有 96 个探针没查到漏依赖）**：
  - 键看得见的读法只有三种：`require('./字面量')`、`path.join(__dirname, '字面量'…)`、运行时记录。别的写法（`__dirname + '/x'`、给 `__dirname` 起别名、按当前目录读相对路径、`process.cwd()`、`require.resolve`）在第一次带记录运行前不在键里，记录丢了也不在。`探针登记检查.py`（`检查.sh` 每次都跑）会拦：同步探针及其静态依赖里出现这些写法、没审过的动态读取、读 `mv_oracle` 之外没登记进 `PROBE_INPUTS` 的文件、没归类的环境变量，都报出来并写明改哪张清单（都在 `incremental_sync.py`）。
  - 运行时记录不分整轮还是只跑几个单元。所以动态读取（`REVIEWED_DYNAMIC`）要保证同一条命令每次读到的 mv_oracle 文件都一样、与单元／分段／环境无关，才能登记；做不到就改成字面量写法。
  - 会改变产物的环境变量登记进 `SWITCH_ENV`（现有 `XIYOU_HBOOT_FILE_XHR`）：设了才进键、只进读它的探针，没设时键不变。带回退开关同步会让读它的探针重跑（hboot 的开关是全部 96 个），跑完不带开关再同步又会重跑一遍，这是对的：两种产物不能互相冒充。
  - 影响面声明：`rerun` 写探针文件全名，工具逐项核对（写错直接报错，不同步）；把 helper 哈希写进产物的探针必须在 `rerun` 里（`event_state_probe` 记 hboot／fs_guard／manual_sandbox／source_identity 四份）。**声明行只增不删**：缓存条目里存的是折算后的 from，删掉仍在生效的行或设 `XIYOU_HELPER_SCOPE=0` 会让其余探针全部重跑；helper 再改时接着写下一行（from＝上一行的 to）。
  - 改了分片探针的单元划分、单元核对、单元摘要（`units`／`plan`／`_verified_units`／`_unit_digests`／`record`），`测试增量同步.py` 的钉值会挂：改了单元含义就把 `SHARD_TOOLING_REVISION` 加一，否则只更新钉值。
  - 改键算法的验收：在主工作区真实缓存上只读重算全部探针的键（`ProbeCache(...).key(条目的 command)` 对 `incremental-cache.json` 里的 key），逐个相同才交（这次 96／96）；键里新增的输入做成「没设／没有时键逐字不变」，否则合并后第一轮同步整份重跑。
  - 已知边角（没改）：动态探针第一次留下记录的那一轮如果同轮别的探针失败，它的暂存键对不上，下一轮会再跑一次（现在只可能是 slice_probe 整轮、shared_system_probe）。

**troop 探针按用例增量（tools-probe-deps2 哪吒，阶段①）**：`troop_event_probe.cjs` 整轮约 1 小时（1400 多例，单进程），原来探针文件加一例就整份重跑（rules-gaps 一类车道每交一批都踩）。现在用例清单拆到 `mv_oracle/troop_event_cases.cjs`（只许列用例：敌群号常量表和对 `api.run／runEventRandom／runParty／runSkillCE` 的调用，不许改引擎或原版函数），探针本体（含 `run()` 怎么跑、怎么记）留在 `troop_event_probe.cjs`。
- 用例键＝用例描述的 SHA-256：`run()` 的全部参数、换队伍／事件随机的上下文、调用方补的 `variant` 等标签。探针先把清单规划一遍（`run()` 只返回描述，不开战，几秒），算出全部键，再真跑。同描述的多例按出现次序加 `#n`。
- 公共指纹 core＝缓存键去掉用例清单文件那一份（`ProbeCache.key(command, exclude=…)`）：来源全文件、探针本体、helper（按影响面声明折算）、Node、环境都在里面，任何一个变了所有用例重跑。缓存键没命中进到 `run_troop_sharded` 后：已发布的 `generated/oracle/troop_events.json` 在键账（`.sandbox/troop_event_keys.json`，`KeyHistory` 版本 1，按结果文件 SHA-256 认领）里认得、core 相同，就把「上次结果＋键表」交给探针，只跑新增或描述变了的用例，其余原样取回，结果与整份重跑逐字节相同；账上认不出或 core 变了就整份重跑（日志第一行写明原因）。
- 抽查：取回的用例每 100 个抽 1 个（第一个必抽，`XIYOU_TROOP_CHECK_EVERY`）真重跑比对，不同就打 `TROOP_INCREMENTAL_MISMATCH`、本轮整份重跑（结果仍然对，但说明键漏了依赖，要查）。
- 每日审计：键账里记 `auditedAt`（上次整份重跑的时刻）。超过 `XIYOU_TROOP_AUDIT_HOURS`（默认 24，0＝不审计）小时，这一轮整份重跑，并把「键相同的用例」逐个与上次结果比对，有不同就失败（退出码 3，`TROOP_AUDIT_FAIL`）——指纹漏了依赖或探针不确定，先查清再同步。整份重跑（没取回任何用例）算一次审计。`XIYOU_TROOP_AUDIT=1` 手动强制审计（直接跑探针时）。
- 合并：车道的键账随 `新建工作树.sh --补齐`（`--carry-cache`）带进车道、车道已有账时并账；`--from-worktree` 克隆车道产物时把车道的 troop 键账和事件状态摘要账并进 main（报告 `fromWorktreeKeyBooks`），否则合并后 main 认不出克隆来的结果，下一次探针改动整份重跑。

**事件状态探针：探针代码改动影响面声明＋每日审计（tools-probe-deps2 哪吒，阶段②）**：事件状态探针的变体指纹里原来含整份 `event_state_probe.cjs` 的 SHA，探针改一行（哪怕只是加一个只有新变体用得到的预设键）全部约 2.4 万个变体整份重跑，约 90 分钟。现在可在 `03_转换工具/probe_change_scope.json` 声明：`{"changes":[{"file":"mv_oracle/event_state_probe.cjs","from":<改前整份 SHA-256>,"to":<改后>,"presetKeys":["maxLevel","actors.*.forget"],"why":"…"}]}`——这次改动只影响预设里带这些键路径的变体（数字键写成 `*`，`presetKeys` 空＝不影响任何变体）；别的变体算指纹时把探针文件当作还是 from（可连成链：下一次改动 from＝上一行的 to），原样取回。最新那条声明（to＝当前探针 SHA）的每个键都要在至少一个变体（event_presets.json 全部预设）的键路径里出现，否则探针直接报错——键拼错或数字键没写 `*` 会让声明变成「不影响任何变体」、该重跑的被取回（审查 76 P3-2，tools-probe-scope1）。
- 声明是人写的断言，**新增条目按甲档交叉核查**：改动要真的只走这些键触发的分支，公共路径（快照、delta、启动）动了就不能声明。写错的兜底有两层：取回的变体照旧每 100 个抽 1 个重跑比对；同步每日一次审计（`XIYOU_STATE_AUDIT_HOURS`，默认 24，0＝不审计）——键账里记 `auditedAt`，到期这一轮整份重跑并把「指纹相同的变体」（结果与读到的地图）逐个比对，有不同就失败（`STATE_AUDIT_FAIL`，退出码 3）。整份重跑（没取回任何变体）算一次审计；账上旧条目没有 `auditedAt` 的从第一次见到起算。手动：`XIYOU_STATE_AUDIT=1`。
- 声明文件在探针的缓存输入里（`PROBE_INPUTS`），格式错探针直接报错；`to` 对不上当前文件的条目不生效。回归在 `测试事件探针分段.py` 的 `StateScopeTests`（临时拷一份探针目录改一行：不声明就全部重跑、声明后全部取回且逐字相同、声明的键命中则只重跑那些、格式错报错、被改坏的结果审计抓得到而抽查抓不到）。

**携带、隔离与分难度（扩角色同步提速第一期，沙僧 2026-10-21）**
- 携带：`新建工作树.sh`（含`--补齐`）经`incremental_sync.py --carry-cache`把主工作区`.sandbox/`的起始种子`save`、`macport`与已发布的`incremental-cache.json`克隆到车道，车道首轮同步就能命中主工作区已跑过的探针。只在车道还没有同名文件时携带，不覆盖车道现场；种子或缓存含符号链接时拒绝携带。缓存记的是输入与产物SHA，车道切片、探针或产物变了照样失效，携带不会让旧结果冒充新结果。
- 未命中诊断：每个要重跑的探针在同步日志里打一行`CACHE_MISS {"probe":…,"reasons":[…]}`（`cache-missing`、`probe-not-cached`、`common-input`、`input-fingerprint`、`output-sha`、`troops`／`events` 单元变化等），同步报告`probes.missReasons`记同样内容；车道没命中时先看这行，不要直接`--full`。
- 隔离：同步给每个探针（切片的每个难度也算一个）单独的存档目录`.sandbox/run/<探针>`，开跑前复制`.sandbox`现有的`save`／`macport`，各探针看到同一份起始状态、互不污染；经`XIYOU_ORACLE_SANDBOX`传给`hboot.cjs`。手动直接`node <探针>`时由`manual_sandbox.cjs`每次新建`.sandbox/manual/probe-XXXXXX`副本（约10 MB），公共种子同样不被改写；同步时顺带删掉12小时没动过的旧副本（报告`prunedManualCopies`记删了几份）。
- 分难度：`slice_probe`拆成六条一难度一条的命令，与其它探针排在同一个`SYNC_JOBS`池里并行，每条还要先占`并行测试.py`的跨工作树共用槽（`CHECK_GLOBAL_JOBS`），几条车道同时同步加测试也不超上限。六份`slice_d<N>.json`各自按敌群分片增量，与全量逐字节一致。
- 共用槽按权重占（期五，2026-10-25 哪吒）：本机16GB／8核，`event_probe`一个进程常驻约4.5GB、堆上限10GB，按1槽算时四个槽可能同时塞进两个它加两场测试，负载冲到40～65、测试进程被系统杀掉。现在`同步正式西游.PROBE_WEIGHTS`给它3槽（共用上限4），没列的探针占1槽，`XIYOU_PROBE_WEIGHTS='{"x_probe.cjs": 2}'`可临时覆盖、超过上限按上限算。多槽进程先独占`slots/heavy.lock`再一槽一槽攒，攒到的不放；单槽进程每次占槽前对`heavy.lock`取共享锁，有多槽进程在攒槽就让路，所以空出来的槽一定归它，单槽进程插不了队，也不会两个多槽进程各攒一半互相等死。同步结尾的`godot --import`、`检查.sh`与`新建工作树.sh --补齐`里的导入也先占1槽（shell 里经`07_开发环境/占槽.py [--weight N] [--label 名字] [--notice-fd FD] -- 命令…`）。
- 单槽先来先得（2026-10-28 哪吒_5）：原来谁轮询先谁拿，主工作区批测占满上限时它的线程放槽后同一瞬间重抢，别的工作树每 0.5 秒轮询一次几乎抢不到（10-28 哪吒排 1 小时、八戒排 1.5 小时）。现在单槽申请前先看 `slots/queue/`：别的进程有更早登记、还活着的等槽者就让一轮；自己第一次没占到才登记（文件名＝开始纳秒_pid_线程，等待中每轮刷新，30 秒没刷新或 pid 已不在的作废）。同一进程的线程之间不排队，多槽进程照 heavy.lock 规则不参加。`XIYOU_SLOT_QUEUE=0` 回旧行为。只对用上新 `并行测试.py` 的进程生效：主工作区还在跑旧版时它照旧抢。
- 总装优先（2026-10-30 哪吒_9）：10-29～30 总装合并选测日志长时间「等槽 4，在跑 无」，四个槽被车道同步／测试占着，一次选测排 40 分钟～1 小时多。现在主工作区（`git-dir` 与 `git-common-dir` 相同；或 `XIYOU_SLOT_PRIORITY=1`）的占槽请求登记在 `slots/priority/`，别的工作树的单槽申请只要看到活着的优先等候者就让（不论先后，即使有空槽），车道多槽进程（同步 `event_probe`）在拿 `heavy.lock` 前也先等它走完；优先等候者之间照先来先得。已占到槽在跑的不打断，所以总装最多等车道手上那几个测试／探针跑完。`XIYOU_SLOT_PRIORITY=0` 让主工作区也按普通排队。代价：总装选测期间车道的测试和同步整段停住，选测一结束就接着跑。
- 探针心跳（2026-10-26 哪吒）：同步等探针期间每60秒（`XIYOU_PROBE_HEARTBEAT`，0关闭）为每个在跑的探针打一行`PROBE_RUNNING={"probe":…,"command":[…],"seconds":…}`（秒数含等槽），`event_probe`整轮约100分钟一行不出也不会被无输出看门狗误判卡死。
- `长任务.py`停任务时`killpg`在macOS上遇到组里有发不了信号的成员会抛`PermissionError`，原来包装器直接崩掉、状态停在running（悟空 sync11）：现在接住后逐个给进程表里属于该组的pid发信号，停不干净也照写终态（status与`.exit`）。
- 等槽心跳：排队期间每60秒（`XIYOU_SLOT_HEARTBEAT`）往标准输出打一行`等槽：<探针或导入> 已等 N 秒（占 k 槽，共用上限 4）`，`长任务.py`的无输出看门狗据此算作有进展，排队再久也不会被判卡死；`并行测试.py`自己的5分钟进度心跳照旧。
- 回归：`07_开发环境/测试角色同步提速.py`（已接进`检查.sh`），夹具全在临时目录，探针排队用测试自己的共用槽状态目录，不受机器上正在跑的同步、检查影响。

每次同步在`04_验证/本地结果/自动同步/`新建备份后只留最近3份（含本次，用户2026-10-18定），删掉的目录名记在同步报告`prunedBackups`。命中还必须逐文件核对当前oracle产物SHA。强制／失效探针开跑前先移除其旧缓存，失败、漏出、新错误不会退回上次成功记录。**探针暂存（哪吒 tools79，2026-11-06）**：某轮有探针退出非零时，同轮已成功、产物核验通过（在、能读、没有新增或变化的错误）的整探针，把产物和本轮缓存键存进 `mv_oracle/.sandbox/probe-stash/`（`index.json` 记键、命令、产物 SHA）；generated 照旧不动、缓存照旧不发布。下一轮该探针键没变、暂存产物 SHA 对得上，就不重跑，日志记 `STASH_HIT`，拿暂存产物和新跑的结果一起照常核验、发布、记缓存，发布后清掉暂存。`--full`、分片增量（`CACHE_PARTIAL`）的探针不用暂存；键变了或暂存被改照常重跑。回退：删 `run_probes` 里 `stashed` 的判断（`load_stash() if cache and not cache.force else {}` 改成 `{}`）即可，暂存目录可直接删。已冻结事件基线里相同的未完成／错误记录保留原样，不能扩称通过；新增或变化错误一律失败。同步中输入变化或来源核验失败时不发布缓存；测量有变化未接受（退出码2）或导入失败时仍发布探针缓存（产物是按这组输入如实测出的）。导入失败不写可复用指纹；只差测量接受（来源核验、导入、缓存发布都成功）时写**待接受指纹**（`sync_stamp.json` 带 `pendingAcceptance: true`，2026-11-07 同步提速）：总装 `--from-worktree` 照常核对转换工具摘要与产物摘要后克隆车道产物，再按 main 自己的同步基线比较，接受单、`--accept-additions`、`--accept-source-switch` 规则不变（没接受照样退出码2，main 不留指纹、不登记），省掉整轮重跑探针（11-07 换源合并因此重跑约 3.5 小时）。回退：`XIYOU_REUSE_PENDING_STAMP=0`（车道不写、合并不认待接受指纹）。

探针缓存与测量接受分开：每个generated路径在第一次覆盖产物前，把已接受的oracle和来源manifest原子保存到`04_验证/本地结果/同步基线/<路径摘要>/`。它在generated与三份滚动备份之外，拒绝、来源核验／导入／缓存／指纹写入失败后都保留。后续缓存命中、`--full`和`--from-worktree`仍对这份基线比较测量及旧来源，不能把上轮拒绝的结果当成已接受。只有测量撤回到基线，或同源只新增经`--accept-additions`接受（既有用例只多出字段、原字段逐项不变也算新增），或既有用例改变经`--accept-changes`接受单逐条接受，且整轮成功后才清除活动基线；下轮从当前已接受产物重新建立。克隆预检失败不建基线、不改产物。基线损坏则保留现场并停止，不回退采用当前generated。

合理的既有测量改变（如有意修正探针）的正式接受入口是`--accept-changes <接受单.json>`，不要手删基线目录：从拒收那轮的同步报告`changeCandidates`里挑出人工核过的条目，逐条补`reason`，写成`04_验证/测量接受/<分支名把 / 换成 _>.json`并提交（格式见该目录README）。每条须与本轮变化的键、变了的字段、旧新摘要逐项相同且每条都用上，只接受单条既有用例的改变（删除、同键多条、非用例字段、新增或删除整份参照、新行有错误都不行），还须同源、来源核验通过，同轮有新增用例时另加`--accept-additions`；否则整轮拒收、基线照留。成功后同步报告记`acceptedChanges`（含理由与接受单SHA-256），本机`本地结果/测量接受记录.jsonl`追加一行，`合并车道.py`合并时把车道带来的接受单传给main的同步。

同步及`检查.sh`默认自动经过`长任务.py`，输出`TASK_LOG=<绝对路径>`。日志最后一行为`TASK_RESULT=<JSON>`，旁边有`.exit`纯整数退出码及`.status.json`任务身份／状态。默认日志在本地结果的任务目录，可用`XIYOU_TASK_LOG`指定本轮日志路径。返回码保留原任务退出码；静默超过默认3600秒标stuck并终止自己创建的进程组，`TASK_IDLE_TIMEOUT`可调整。

车道／总装统一等待：`07_开发环境/等待任务.sh <日志>`。成功返回0，失败返回原非零码，卡住返回124；标记／退出码不一致返回2。`--timeout <秒>`只限制本次等待，不把仍运行的任务误标失败。新一轮任务有新的runId，旧结果不能当成新一轮成功。用日志锁识别包装器是否仍在运行，不凭PID存在判断；包装器失联后，等待器先核对本次子进程组身份并清理残留，确认退出才写stuck终态。缺少身份、身份改变或仍有残留时，标orphaned并返回2，不写完成标记／退出码，同一日志拒绝重跑；此时不能据此认定任务已结束。工具只管理自己启动且能确认身份的进程组。

要让任务不随启动它的会话一起停（Remote Control 会话空闲被停会带停其子进程），改用`python3 07_开发环境/长任务.py start <日志> -- <命令及参数>`：macOS 上它把`run`交给 launchd（`launchctl bootstrap gui/<uid>`，不保活，环境变量与工作目录照搬）起，任务的父进程是 launchd、macOS「责任进程」是它自己，发起它的 claude 会话被关时不会被连带 SIGTERM（哪吒 tools81：原来只用 start_new_session，责任进程仍是 claude，换源同步两次 143；`XIYOU_LONG_TASK_LAUNCHD=0` 或没有 launchctl 时退回新会话子进程）；已结束作业的登记由`wait`看到终态时和下次`start`时卸掉。launchd 作业的 stderr 落在每用户临时目录（`$TMPDIR/<作业名>.err`），`run`起来后自己接回`<日志>.start.err`：日志在 ~/Documents 下时 launchd 打不开那里已存在的文件（受隐私保护，系统日志「Unable to open stderr path … Operation not permitted」，作业 EX_CONFIG 一起来就消失；tools82）。作业没写出状态就结束时，`start`打印原因（last exit code 与作业 stderr）并退回子进程方式。等状态文件写出本轮启动令牌后打印`TASK_LOG=`就返回，`run`自身的报错在`<日志>.start.err`；之后照常用等待脚本，宜在前台加`--timeout 540`反复等。

其他长任务可显式启动：`python3 07_开发环境/长任务.py run <日志> --idle-timeout 1800 -- <命令及参数>`，再用同一个等待脚本。运行、失败与卡住回归只在临时目录和自建子进程里进行。
