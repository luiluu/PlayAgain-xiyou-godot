# 更新清单生成说明（`07_开发环境/生成更新清单.py`）

比较新旧两个版本目录，写出这次补丁改了哪些文件（路径、字节数、SHA-256）、删了哪些文件、新版本号、底包号、最低基线版本，并用仓库外的私钥签名。cc pro-update-manifest，2026-11-11。

方案见私密仓库 `重制设定/重制版_自动更新方案_v0.2.md`：签名清单、补丁放用户数据目录（和存档同级）、Gitee 为主源、GitHub＋jsDelivr 当镜像、首个可打补丁的基线是合并自动更新之后出的下一个整包。

## 和 `发布补丁.py` 的关系

| | `生成更新清单.py`（本工具） | `发布补丁.py` |
| --- | --- | --- |
| 输入 | 新旧两个版本目录 | 当前工程＋一个底包 `.pck` |
| 输出 | `patch_manifest.json`／`.sig`／`patch_files.txt`：逐文件的改动清单 | `channel.json`／`.sig`：玩家客户端读的版本清单，补丁 `.pck` 和下载地址 |
| 要 Godot | 不要 | 要（`--export-patch`） |
| 碰发版仓库 | 不碰 | `--stage` 时在本机提交，不推送 |

本工具是发补丁前的核对单：这一版到底改了哪些文件，删了的文件补丁带不走（叠加载入只能加和换，删掉的文件在底包里还在，要看会不会出问题），体积大头在哪。签了名的清单可以和补丁一起存档，交叉核查时拿来对。客户端不读它。

## 用法

```bash
cd 03_再刷重制_Godot/07_开发环境

# 1. 出清单并签名（私钥路径用参数给，放在仓库外）
python3 生成更新清单.py \
  --old <旧版本目录，比如 dev470 的工程导出> \
  --new <新版本目录> \
  --key "<私钥.pem 的路径>" \
  --out ../05_发布/补丁/清单_dev471

# 2. 回头核对：验签，并核对新版本目录和清单是否一致
python3 生成更新清单.py --verify ../05_发布/补丁/清单_dev471/patch_manifest.json \
  --pubkey <公钥.pem> --new <新版本目录>
```

参数：

| 参数 | 作用 |
| --- | --- |
| `--old`、`--new` | 旧版本（补丁要叠上去的底包）和新版本的目录。目录里有 `content/build_info.json` 就从它读开发编号 |
| `--old-code`、`--new-code` | 目录里没有 `build_info.json` 时给编号；新编号必须比旧的大 |
| `--key` | 签名私钥 `.pem`。也认环境变量 `XIYOU_UPDATE_KEY`。没有默认位置；私钥在本仓库里面会被拒绝 |
| `--unsigned` | 只出清单不签名，预览用，不能发；会删掉输出目录里上一次的旧签名 |
| `--out` | 输出目录。放仓库外，或仓库里被 `.gitignore` 忽略的 `05_发布/补丁/` 下；仓库里没被忽略的位置会被拒绝 |
| `--min-base` | 最低基线版本，默认等于旧版本编号；可以调低（更老的底包另有自己的补丁时），不能高于旧版本编号 |
| `--first-patchable` | 首个可打补丁整包的编号，知道了就给上：旧版本编号和最低基线都不能低于它 |
| `--allow-no-loader` | 旧目录里没有补丁载入器也照出（只给测试或解开的非工程目录用） |
| `--exclude` | 再排除的相对路径通配，可多次；目录写 `名字/`。默认已排除 `.git/`、`.godot/`、`__pycache__/`、`.DS_Store`、`Thumbs.db` |
| `--skip-embedded-check` | 不核对游戏内嵌公钥，只在用临时密钥试的时候用 |
| `--date` | 清单日期，默认今天 |
| `--verify`、`--pubkey` | 验一份已出的清单；再给 `--new` 就逐个比对文件 |

## 清单格式

```json
{
 "schema": 1,
 "kind": "xiyou-patch-files",
 "version": "0.471",
 "code": 471,
 "base_code": 470,
 "min_base": 470,
 "date": "2026-11-11",
 "files": [
  {"path": "core/changed.gd", "change": "modified", "size": 10, "sha256": "…"},
  {"path": "modes/xiyou/data/新增.json", "change": "added", "size": 7, "sha256": "…"}
 ],
 "removed": ["modes/xiyou/data/old_only.json"],
 "total": {"files": 2, "bytes": 17, "removed": 1},
 "excludes": [".git/", ".godot/", "__pycache__/", ".DS_Store", "Thumbs.db"]
}
```

- `version`／`code`：新版本，玩家看到 `0.<开发编号>`，和 `channel.json` 一致。
- `base_code`：这个补丁相对的底包编号（旧目录）。
- `min_base`：低于它的底包不能装补丁，要去 QQ 群下整包。
- `files`：只列新增和改动的文件，按路径排序；路径统一成 NFC（Mac 上的中文文件名是 NFD，不统一会被当成改名）。
- `patch_manifest.sig`：对 `patch_manifest.json` 原始字节的 SHA256withRSA 签名，和 `channel.sig` 同一算法，`openssl dgst -sha256 -verify <公钥> -signature patch_manifest.sig patch_manifest.json` 也能验。
- `patch_files.txt`：只有路径，一行一个。

## 拦住的情况

- 旧目录里没有补丁载入器（`core/boot_patch.gd`，或导出后的 `.gdc`／`.remap`）：dev384 那种已发的包装不了补丁，首个可打补丁的基线是下一个整包。
- 新编号不比旧编号大；两个目录完全一样；`--old` 和 `--new` 是同一个目录。
- 最低基线高于旧版本编号；给了 `--first-patchable` 时旧版本或最低基线低于它。
- 没给私钥（又没加 `--unsigned`）；私钥在仓库里；私钥对应的公钥和新版本 `core/update_check.gd` 内嵌的不是一把；签完用公钥验不过。
- 目录里有符号链接；两个文件名统一成 NFC 后相同。

## 密钥

- 仓库里不放任何私钥。真私钥只在 Kyo 的 Mac 上仓库之外（`发布补丁.py` 的默认位置在 `~/Library/Application Support/KYO/发版密钥/`），用的时候 `--key` 指过去。
- 测试 `07_开发环境/测试生成更新清单.py`（13 项，进 `工具回归.py` 和 `检查.sh` 的 tools 组）每次临时生成 RSA 密钥，跑完随临时目录删掉，不碰真私钥、不联网。
