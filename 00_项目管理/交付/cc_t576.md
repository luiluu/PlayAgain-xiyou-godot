## 结论（一句话）

小o 报的第 1271 帧（发行口径 331～347 ms）是第二次强制行动 8153「逐浪·再释放」：给我方全体回 HP／MP／TP 并挂 1121。插桩拆下来，大头不是 T574 判断的「挂状态整体作废」（挂状态只占约 15 ms），而是 30 次资源回复。每写一次资源、gain 末尾标脏一次、refresh 末尾被动缓存换新一次，缓存就整体作废，接着读生命／魔法上限要整套重算能力值（这一次行动 404 次），每次都现算一遍技能 id 表（455 次，约 0.2 ms 一次），技能记录也重建（79 次）。本单让技能 id 表在战斗里跨这几种「轻写入」保留，记录也不再跟着换代。发行口径三遍取大，最长帧从 T576 之前的 365 ms 降到 256 ms，同口径玩家 v0.04.04 是 277 ms。

## 2. 根因（第 1271 帧插桩拆分）

强制行动 8153（scope 8，我方全体）：每个目标回 HP、MP、TP 各一次，再挂 1121（STATE_TRAITS）。`execute` 共 365 ms（插桩下），其中：

| 段 | 含子调用 |
| --- | --- |
| 30 次资源回复 `XResourceContext.gain` | 183 ms（前后快照 101 ms、写入后 refresh 110 ms，有重叠） |
| 伤害／回复公式 `_calculate_damage` | 49 ms |
| 挂状态 `add_state`（15 次 STATE_TRAITS） | 15 ms |

- 一次 gain：前快照（读生命／魔法／TP 上限）→ 写资源 → refresh（窗口里再读三项上限、重建被动缓存，末尾 `passive_touch`）→ `param_mark_dirty`（`read_touch`）→ 后快照（再读三项上限）。HP／MP／TP 写入器、`passive_touch`、`param_mark_dirty` 每一下都作废只读窗口，所以每次读上限都整套重算能力值：这一次行动 `_param_now` 404 次。
- 角色的能力值重算要读被动（`passive_values` → 技能表缓存项），缓存项每次都要先现算 id 表来比对：`_skill_ids_now` 455 次（250 次来自 `param_base`，其余来自被动缓存重建、状态抵抗、sparam／xparam 等）。`passive_touch`、`read_touch`、`state_touch` 都让 `_skills_epoch` 换代，技能记录跟着重建 79 次。
- id 表不读 HP／MP／TP、被动缓存、不带技能的状态（O-398 交付时已逐个核过各 skills 包装，`XBattler.state_class` 的注释），这几样写入之后重算 id 表、重建记录都是白算。
- 同口径（无插桩，各两遍）的方案比较：A1 只跨 HP／MP／TP 写入保留 id 表，282／280 ms（压线）；A4（定案）再加非 STATE_HARD 状态、`passive_touch`、gain 那一处标脏不换代，250／249 ms；A3 把 `param_mark_dirty` 全部 76 处都改轻，和 A4 一样（255／254 ms），但风险面大得多，没采用。
- 剩下的：本单之后第 1271 帧 id 表只现算 5 次，其余是能力值本身重算（`param_plus` 52 ms／404 次、特性集合、被动值读取等，见 `发行口径帧耗.txt`「## T576」段）。要再压得减少读上限的次数或给能力值做跨写入缓存，后者要把所有写入点登记全才安全，本单不做。
