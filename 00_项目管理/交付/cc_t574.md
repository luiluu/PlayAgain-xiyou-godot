## 2. 根因

1. **事件里的强制行动一帧算完（第 1248 帧）**：`XBattleLogic._drive_events` 碰到 339 就在当场结算（`XBattleEventRunner` 返回 `forced_action`），然后接着往下跑，同一次 `troop_events` 里的几次强制行动都在同一帧算完。原版 `command339` 是 `setWaitMode('action')`，要等这次行动演完才往下执行。普通行动从 T225 起按段结算，强制行动没有，所以四倍速下这一帧特别显眼。T506（O-667，`75a09ded2`，补丁线 v0.04.05）让自动战斗也会放朵莉亚「逐浪」、绯红蔷薇「蔷薇领域」这类带追击公共事件的治疗技，所以这件事从 v0.04.05 起在自动战斗里经常出现。
2. **技能 id 表里的专武检查拼大表**：`XActor.has_absorb_weapon`（技能 id 表每建一次都要问，专武·特效吸取 10455）把自己、整个背包、全队其他人的装备拼成一张新表再逐件查，背包装备多时一次 0.16～0.38 ms。T572 之后一次行动仍要建一两百次 id 表，这一项占发行口径单次行动约 10%。
3. **`XDB.rec` 层层判档**：取一条记录要过二十几层天启篇改写（号卷、教派、境界、技能重构、通用书、元素、功法……），每层各自判一次 `XTianqi.active`，西游档全部判否。开发工程 9.3 µs／次（原表直取 0.3 µs），发行空壳里这些层是空壳、本来就便宜一些，占单次行动约 4%。任务里说的 `XTianqi.active` 每场 250 万次，大多出在这里。
4. **给全队挂状态（本单不做，另开卡）**：每加一个状态都 `state_touch` 换代，所有角色的只读窗口和技能表缓存一起作废，接着 refresh 现读三项上限，整张技能表重建。「蔷薇领域」这种招一次行动 id 表要现算 200～250 次。改作废范围要动 `state_touch` 的语义，风险高，协调同意另开卡，不进这次补丁。修完 1～3 后剩下的 180～240 ms 长帧都是这一类（第 4 节）。

## 3. 修法（三个回退开关，默认开）

1. O-待定-4 `XBattleLogic.FORCE_YIELD`（`battle/battle_logic.gd`、`battle/battle_scene.gd`）：事件里每做完一次 339 强制行动，解释器就停住（`_waiting = {token, yield: true}`），不写新记录、不选页、不碰战斗状态；战斗画面 `_play_troop_events` 把这次的记录演完，再 `resume_event` 接着执行下一条指令。所以结算的先后、记录与原来逐条相同，只是分到了几帧里。只有开了 `yield_forced` 的宿主会停，目前只有战斗画面开（`XBattleScene.setup`）。无界面的 `run_events`、直接调 `troop_events` 的测试和虚拟玩家照旧一次跑完（`run_events` 碰到停顿也直接续上）。停顿续上时不走「340 之后确认文字」那一支，和原来的行为一样。
2. O-待定-5 `XActor.ABSORB_SCAN_FAST`（`core/actor.gd` `has_absorb_weapon`）：先看 `_absorb_ids` 有没有哪把开放专武写了本人，没有就一定是假；有的话按原来的范围逐处找（自己、背包、其他人），不拼新表。只读判断，不分先后，结果相同。
3. O-待定-6 `XDB.XIYOU_REC_FAST`（`core/xdb.gd`）：西游档（含没有存档）取表内记录（0 < id < 表长）走快路，只过西游档会改的三层：`_tq_always` 的天启篇专属招（`XTianqiSkills.rec`）、西游档徐凤年重做（`XXufeng`）、离群削弱（`XXiyouNerf`）。其余各层的判断都要求天启篇档，在西游档原样返回。表外号段走原链；道具、公共事件有西游档才改名的乌鸦配方（`CROW_BLUEPRINT_*`），也走原链。天启篇档不走快路。
