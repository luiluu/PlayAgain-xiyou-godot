# 提案：星级仓库（Star_Warehouse 通用仓库）移植（2026-10-27，八戒_77）

- 状态：提案，待沙僧审。只写方案，不实现。
- 起因：Map041 黄金大厅 EV1「通用仓库管理员」的「存放／取出」两项调用 `Scene_StarSaveWarehouse`／`Scene_StarWarehouse`。这是跨存档的通用仓库，重制只有 PH_Warehouse（`XWarehouse`），所以 41 没进切片。
- 依据：冻结 v0.28 `js/plugins/Star_Warehouse.js`（701 行，插件表第 122 位，参数 DCL1～5 = 1／1.5／2／2.5／3，DCL1Jc～5Jc 都是 100），以及数据里所有调用点：Map041 EV1、Map060 荣耀殿堂 EV2、Map001 EV1／Map004 EV41／CE714 的难度标记。

## 一、原版行为

### 1. 插件一共做了五件事，不只是仓库

### 2. 存什么、怎么存

- **装备**：`ConfigManager.GetEq` 是数组，元素是整件装备的数据对象（YEP 独立装备的 `$dataWeapons[id]`／`$dataArmors[id]` 那份，名字、属性、特性、备注、meta 都在里面）。
  - 存放：只列背包里的（`$gameParty.armors().concat(weapons())`，防具在前，身上穿着的不列）；备注带 `<PushDct>` 的弹提示「不可存放」。存进去以后 `delete $gameParty._weapons[id]`，把这一 ID 整个删掉。独立装备一个 ID 只有一件，所以等于拿走这一件。
  - 取出：给这件装备分配新 ID（`$dataWeapons.length`），push 进 `$dataWeapons` 和 `DataManager._independentWeapons`，背包加 1，再从 `GetEq` 移除。
- **宠物**：`ConfigManager.GetPet` 是数组，元素是整只宠物（`Game_Enemy` 对象，序列化后丢了原型，取出列表刷新时用 `new Game_Enemy(1).__proto__` 接回去）。
  - 存放：列 `$gameParty.Pets`；出战宠物（`GTWar`）点了没有任何反应（不提示、不蜂鸣），其余从 `Pets` 移到 `GetPet`。
  - 取出：push 回 `Pets`，从 `GetPet` 移除。
- **容量**：没有上限，也没有数量显示，每项就是一件或一只。
- **只有装备和宠物两类**，道具、重要物品不能存。源码注释写着「存档装备数据不互通 去除装备」，但装备那一项其实还在。

### 3. 跨存档存储的位置和格式

- 存在 MV 的配置文件里（`ConfigManager.makeData` 加了 `GetEq`、`GetPet`、`DCultyLA～LE`、`CurrencyWarehouse`），Mac 版对应 `save/config.rpgsave`，和 `DataManager.saveGlobalInfo` 无关（那段已被注释掉）。
- **什么时候写盘**：仓库画面自己**不调** `ConfigManager.save()`。冻结源里调它的只有：关设置画面（`Scene_Options.terminate`）、键位设置、GhostButtons、成就／测试模式、显示偏好、技能升级提醒、弱者挑战等几个 Codex 运行时。存档（`DataManager.saveGame`）**不写配置**。所以 NPC 说「保存以后可以在其他存档取出」与实际不符：要等下一次配置写盘，东西才真正落到文件里。
- 由此带来原版的两个缺陷（第三节有处理建议）：
  1. **丢东西**：存放后没有触发任何配置写盘就退出，存档里东西已经没了，配置文件里也没有，等于消失。（要是存放后存了档，存档里同样没有。）
  2. **复制**：存放后配置写了盘，但没有存档就读回旧档，旧档里东西还在，仓库里也有。取出同理，可以反复刷。
- `CurrencyWarehouse` 只在 makeData／applyData 里出现，数据里没有任何地方用到，不移植。

### 4. 两个画面的布局与操作（两个画面结构相同，只差数据来源）

都继承 `Scene_ItemBase`，1280×720：

- **说明窗**（`Window_Help`，两行）在顶部：装备显示说明；宠物是 `Game_Enemy`，没有 `description`，说明窗是空的（要截图确认）。
- **分类窗**（`Window_StarItemCategory`，`Window_HorzCommand`，宽 1280，两列）：「装备」「宠物」。开场就是激活状态；光标移动时列表跟着切换分类，取消关闭画面。
- **列表**（`Window_StarItemList`）：从分类窗下沿到画面底，两列，间距 48。装备画图标＋名字（`drawItemName`，名字后宽留 `textWidth('000')`，不画数量）；宠物只写 `item.name()`。不画 NEW，没有锁定或置灰（`isCurrentItemEnabled` 恒为真）。
- **操作**：分类确定 → 进列表，光标在第 1 项（`selectLast` 就是 `select(0)`）。列表确定 → 存入或取出一件，刷新后光标不动、不发声（没有装备音效也没有蜂鸣；选中空格时只刷新）。取消 → 回到分类窗、列表去掉光标。
- `createActorWindow` 建了角色窗但从不打开，不移植。
- 各窗口的确切位置、行高、字色、光标在空列表上的表现，以浏览器参照为准（见第四节第 3 条），上面的数是按 MV 窗口公式推出来的。

## 二、重制方案

### 1. 存储：另起一份跨存档文件，照 XGlobalVars 的写法

- **不复用 `XWarehouse`／`XState.warehouses`**：那是存在单个存档里的 PH 仓库（四类、容量、qtty）。通用仓库要跨存档，结构也不同。界面上能借的是 `XWarehouseScene` 的画法，数据层不共用。
- **不塞进 `XGlobalVars`**：它只存插件参数列出的变量和开关，格式是 `{switches, variables}`，开局和读档时整格覆盖。仓库是对象数组，存取时机也不一样，硬塞进去会把两种语义混在一起。
- **新建 `modes/xiyou/core/star_warehouse.gd`（`XStarWarehouse`）**，照抄 XGlobalVars 的骨架：
  - 文件 `<存档目录>/star_warehouse.json`，和 `global.json` 放一起，用 `path_override` 给测试改路径，跟随 `XSave.dir_override`。
  - 格式 `{"version": 1, "mode": "xiyou", "gear": [装备实例…], "pets": [宠物…]}`。装备实例就用重制 `s.gear` 里的那种字典（带 `instanceId`），宠物用 `XPets` 的字典（`pets.list` 里的元素），都是纯 JSON，不用再接原型。
  - 写法：先写 `.tmp` 再改名；按路径只读一次；文件损坏时按空处理，下次改动时整份重写（和 XGlobalVars 一致）。
- **不读 MV 的 `config.rpgsave`**（底线：不迁移 MV 旧存档）。

### 2. 存取逻辑（`XStarWarehouse`）

- `deposit_gear(s, rec)`：只收背包里的独立装备实例（`s.gear` 里有、没穿在身上）；`<PushDct>` 返回 false，由画面弹「不可存放」。从 `s.gear` 移除，加进仓库，**立即写盘**。
- `withdraw_gear(s, rec)`：从仓库移除，`s.register_gear(rec)` 重新登记（实例编号和背包不重复，`XWarehouse.from_save` 已经这么做），放回 `s.gear`，**立即写盘**。原版取出时会重新分配 ID，重制的实例编号由 `register_gear` 负责，效果一样。
- `deposit_pet(s, i)`：出战宠物（`XPets.war_index`）返回 false、不出声（照原版）；其余走 `XPets.release` 同一套序号修正（出战序号前移），再加进仓库，**立即写盘**。共享角色序号 `team_a` 是出战栏位序号，不是宠物序号，不用动。
- `withdraw_pet(s, i)`：append 回 `pets.list`，**立即写盘**。
- 存档时什么也不做：仓库独立于存档。

### 3. 原版缺陷的处理（按「原版可优化处先优化、可回退、用户最后定」）

- **O-待定-1 存取立即写盘**（建议默认开）：原版要等下一次配置写盘，退出就可能丢东西。重制每次存取都立即写盘，NPC 那句「保存以后」不改字。回退：开关改成「只在设置页关闭等时机写盘」，没有价值，所以只登记、不做回退开关也行，请用户定。
- **O-待定-2 复制问题**：立即写盘以后，「存放 → 不存档 → 读旧档」还是能复制（旧档里那件还在）。可选做法：
  - 甲：照原版，不防（跨存档仓库的本意就是在档之间搬东西，原版也能复制）。
  - 乙：给每件装备和宠物盖一个全局唯一的「出仓号」，读档时如果档里有同号物件、仓库里也有，就从仓库删掉。代价是要改读档流程和装备实例结构。
  - 本提案**默认甲**，写进交接板「需要用户决定」。
- 「设为给予装备」的 `[传出]` 是直接改装备名字存进存档的。重制要做 B／C 时，改用实例上的标记字段，显示时再拼上「[传出]」，不污染名字。（只在做 C 时需要，见第 5 条分期。）

### 4. 画面（`modes/xiyou/ui/star_warehouse.gd`，`XStarWarehouseScene`）

- 一个场景，带 `save_mode: bool` 参数（对应原版两个类的 `Save` 标志），说明窗、分类窗、列表照第一节第 4 条。
- 复用：`XMVWindow`（窗口与开合）、`XWarehouseScene` 两列列表的画法（图标、品质色名字、`COL_STEP` 等常量，可以抽成公用函数，但只在本车道动 `ui/warehouse.gd` 的情况下才抽；不然先复制，合并后再收拢）、`XItemScene` 的说明卡（如果参照证明装备说明窗就是普通 `Window_Help`，就直接用 `XHelpCard`）。
- 声音照原版：存取都不出声。这和 PH 仓库（装备音效／蜂鸣）不一样，要在注释里写明，免得以后有人「统一」。

### 5. 事件与切片

- `mv_script.gd` 认 `SceneManager.push(Scene_StarSaveWarehouse)`、`SceneManager.push(Scene_StarWarehouse)` 两种写法（带尾随空格），交给宿主打开画面，和 `PHWarehouse show` 同一条路（`mv_interpreter.gd` 108～111、268 行，`map_scene.gd` 997 行）。
- 插件指令 `SceneManager.push(...)` 照原版当无操作；`PHWarehouse create <通用仓库>` 已经支持，照常建出一个用不到的 PH 仓库（保持和原版存档内容一致）。
- `xiyou_slice.json` 加地图 41。41 只有两个事件：EV1 仓库管理员，EV2 (10,18) 转场到 Map040。由 A 车道扩切片时加入。

### 6. 旧档兼容

- 仓库是新文件，没有旧数据。旧存档不用动，`XState` 不加键。
- 新建 `star_warehouse.json` 前后，旧档读入都不受影响。只有做 B／C 时装备实例会多一个「传出」标记，旧档缺这个字段时按 false 处理。

## 五、顺带发现（不属于本提案）

- **E 难度倍率（已由悟空处理）**：`Star_Warehouse` 包了 `Game_Enemy.param／xparam／sparam`，`$gameParty.DCultyL<N>` 为真时敌人数值乘 DCL<N>（难度 1～5 依次 1、1.5、2、2.5、3）。Map001 EV1 选难度时会把 `DCultyL<N>` 设为真（CE714「难度修复」同样会设），所以正常开局一定带这层倍率。
  - 八戒_77 在原版引擎实测（hboot，只读；Math.random 固定为 0.99；敌人 1；mhp／mat／hit，DCultyL 关→开）：d2 7500／12／0.95 → 11250／18／1.425，d3 → 20000／28／1.9，d4 → 37500／40／2.375，d5 35000／20 → 105000／60／2.85，d1、d6 不变。
  - 重制 `enemy.gd` 原来只乘 Vitsuno_Difficulty 的倍率；战斗参照 `slice_probe.cjs` 不设 DCultyL，所以严格对照查不出来。
  - 悟空_62 期十四（`claude/wukong-challenge2`）独立查到并在修：`enemy.gd` 加 `warehouse_rate`，新探针 `enemy_warehouse_probe.cjs`，新专项 `xiyou_enemy_warehouse`。上面的实测数字与悟空的结果一致，算交叉印证。xparam 乘到 2.85 以后实际有什么效果，由总装转给悟空核。
- **D 通关加成**：`Game_Actor.param × (1 + Σ DCultyLx[1]/100)`，数据在配置里。重制里没搜到 `DCultyLA`。只有 Map060 会设它，Map060 不进切片就不会触发；Map060 入切片时要一起做。
