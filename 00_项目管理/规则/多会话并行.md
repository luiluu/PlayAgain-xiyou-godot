## 多会话并行（用户 2026-10-15）

只开一个会话时不需要本节，照 [AGENTS.md](../../AGENTS.md)「开工与收工」做。同时开多个会话（Claude、Codex，或同一执行者的几个会话）时：

**角色**
- **总装**（1 个，主工作区 `main`）：派任务、维护交接板「车道」表并预分配编号、合并车道分支、合并后跑 `检查.sh --oracle`、写变更记录／交接板／进度账、递增开发编号、触发进度审查、同步正式源。总装自己做事也只在 `main` 上，并且不碰车道的独占文件。
- **车道**（同时最多 2 条写代码的；本机 8 核 16GB，再多会卡在测试上）：每条一个 worktree 和分支 `claude/<任务>` 或 `codex/<任务>`，只改派给自己的独占文件。
- **核查**：不占车道名额，读差异、跑检查即可；核查中要修代码时，修复按一条车道算（或由总装在 `main` 上修）。

**工作者名册**（用户 2026-10-15：主力是两个并行的 Claude；Codex 设计基本框架、做核查，只在 Claude 额度用尽时接力重制内容）

| 工作者 | 执行者 | 职责 | 工作区 |
| --- | --- | --- | --- |
| **唐僧** | Claude | 总装：定路线、派任务、预分配编号、合并、合并后检查、写共用文件、触发进度审查。只在派任务和合并时才动，平时不上手做内容，省额度 | 主工作区 `main` |
| **悟空** | Claude | 车道 A 内容／楼层（扩楼层、事件翻译、敌群事件），重制的主力 | worktree，分支 `claude/<任务>` |
| **八戒** | Claude | 车道 B 界面，或唐僧改派的车道 C 规则／机制 | worktree，分支 `claude/<任务>` |
| **白龙** | Claude | 车道 C 角色／机制（用户 2026-10-25 加开：专属角色等），文件边界见车道表 | worktree，分支 `claude/<任务>` |
| **哪吒** | Claude | 车道 D 检查与合并工具（用户 2026-10-25 加开），不碰游戏代码、切片与转换器 | worktree，分支 `claude/<任务>` |
| **沙僧** | Codex | 基本框架设计、交叉核查（悟空、八戒、唐僧的提交，并复核进度账）、额度接力（见[会话接力与省额度](会话接力与省额度.md)） | 核查用主工作区或只读 worktree；接力时进被接力车道的 worktree |

- 提交信息的执行者行写成 `执行者: Claude（悟空）`、`执行者: Codex（沙僧）`；变更记录标题写成 `【Claude·悟空·未经Codex检验】`。
- 交叉核查仍按执行者分：三位 Claude 的提交都由沙僧核查；沙僧接力时的提交由 Claude（唐僧、悟空或八戒中不是该车道接手者的一位）核查。
- 车道表「执行者」栏写工作者名和会话名，如「悟空（重制_悟空_3）」。

**车道按文件划分**（派任务时在车道表写明独占文件）
- A 内容／楼层：`03_转换工具/xiyou_slice.json`、转换器、事件解释器与脚本翻译、事件对照 baseline、敌群事件。**只能有一条**，因为这几处每层都要改。
- B 界面：界面页面（`scenes/` 下各页）、设置页、`ui_reference`。
- C 规则／机制：战斗逻辑、`mv_oracle` 探针、数值链（严格级对照）。C 和 A 都会碰战斗逻辑与探针，同时开时先在车道表里把文件划清。
- **同步排队（2026-10-25，四车道时本机 M1 Pro 8 核满载）**：启动 `同步正式西游.py` 前先 `pgrep -fl 同步正式西游.py`，有别的同步在跑就先做别的，同一时间只跑一个；专项因 600 秒超时失败先看负载、重跑一次再下结论。
- 首选 A＋B 并行；共用的公共组件只由一条车道改，另一条要用时等它合并。

**共用文件只由总装改**：交接板、变更记录、重制步骤清单、`当前状态.json`、`来源登记.json`、开发编号（`开发编号.json`、`project.godot`、`build_info.json`）。车道要写进这些文件的内容，写进 **交付单** `00_项目管理/交付/<分支名把 / 换成 _>.md`（模板见[该目录 README](../交付/README.md)）；每个分支单独一个文件，合并时不会冲突。
- 编号：优化登记 O-NNN 由总装派任务时在车道表预分配，车道只用分给自己的号。开发编号在合并时才确定，车道在文档里写开发编号占位，总装合并时换成实际编号（占位写法只写在 [AGENTS.md「底线规则」](../../AGENTS.md)，因为合并工具会替换车道改过的文件里的占位；`main` 上的 `检查.sh` 会报出遗留的占位与未并入的交付单）。
- 在 worktree 里运行 `同步正式西游.py` 时自动不写来源登记／当前状态；正式源的登记只在 `main` 上做。

**流程**
1. 派任务（总装）：在交接板「车道」表加一行（车道、执行者、worktree、分支、独占文件、预分配编号、开始时间）并提交，再运行 `03_再刷重制_Godot/07_开发环境/新建工作树.sh <任务名> <claude|codex>`。脚本从 `main` 最新提交切出分支，链接引擎、`node_modules` 与西游资料库，复制 `main` 的转换产物与导入缓存后按本分支重跑转换器和 `godot --import`。桌面 app 自己建的 worktree 用 `新建工作树.sh --补齐 <路径>` 补上这些不入 Git 的文件。**车道会话一律从主工作区启动、由 app 自建 worktree，不再预建**（用户 2026-10-19 要求开会话尽量不经他允许；只有主工作区目录是预先允许的，预建路径每次都要点允许。实测从主工作区启动也可能弹一次允许卡片，只能少弹、不保证不弹）：总装只在车道表登记任务与独占文件，车道交代写明「先跑 `新建工作树.sh --补齐 <自己的路径>`，按自己的分支名写交付单，并在线程里报分支名」，总装收到后把车道表的位置栏改成实际分支。开会话时按[会话接力与省额度](会话接力与省额度.md)「车道模型与强度按任务难度」显式传 `model`／`effort`。
   - **交代先算收益、分期、写停手条件**（用户 2026-10-21，起因：扩角色同步提速交沙僧时角色只剩一两批，沙僧把大半时间花在最难又几乎用不上的「按单元复用」原型上，可交的部分反而没先交）：① 派之前先算收益还剩多少（这项工作以后还会被用几次、离做完还有多远），收益快到头的不派或砍范围；② 交代按「先交可合并的一小期、再做下一期」写，每期单独验收，难的尾巴放最后并写明可以砍；③ 写清什么情况下停手回报（如做到某一步还看不到收益、要等别的车道）。给沙僧和 Claude 车道的交代都照此写。
2. 车道开工：读交接板（只读）与自己那一行；`git status`、`git log` 照常看。中途照常小步提交、`WIP:` 提交到自己的分支；过程中只跑相关专项。车道只在自己的线程里说话：项目聊天或别的线程里的问题不是问自己的，不去回答，除非唐僧转来（八戒_30 2026-10-20：车道读到项目聊天里的问题会偏题回答）。
3. 车道交付：先 `git merge main` 并解决冲突；合并进来的提交改了切片、转换器或探针时，再跑一次 `新建工作树.sh --补齐 <路径>` 让转换产物跟上（转换产物不入 Git）；扩了切片或改了探针的，最后在工作树跑一次 `同步正式西游.py --accept-additions`（留下产物指纹，总装合并时可免重跑；同步结束自动 `godot --import`）；改了切片的再跑 `03_转换工具/内容覆盖检查.py`，看过报告再 `--update-baseline`；**车道不跑全量 `检查.sh`**（用户 2026-10-21：总装合并后统一跑一次就够，车道在 worktree 里全量约 30 分钟、与总装重复）：只跑与改动相关的专项＋必跑项（`并行测试.py <godot> <工程> 名字前缀…`，改了谁就跑谁和直接依赖它的测试；必跑项见[进度审查与验证](进度审查与验证.md)「三级检查」，列进交付单「验证」），写好交付单最后写「可合并」，提交。**扩角色车道（悟空，用户 2026-10-20）**：同步前先只跑角色相关专项（`slice_probe`／`actor_passive_probe` 单探针、`xiyou_actor_p0`、`xiyou_rules*` 中含新角色的难度段、`xiyou_wtype`），有问题当场改，做不了的角色先剔出并写进交付单，最后只跑一轮同步，不做「查出问题→重同步→再查」的重复轮次。长任务（同步、`检查.sh`）用 `python3 07_开发环境/长任务.py start <日志> -- <命令>` 启动：它在新会话里跑，会话空闲被停（Remote Control）也不会带停；然后在前台反复跑 `07_开发环境/等待任务.sh <日志> --timeout 540`（每次在 Bash 十分钟上限内返回，124＝还在跑，接着再等），不靠后台任务通知唤醒（曾因通知没来空转一小时）；返回 2 且状态 orphaned 表示旧任务无法确认已结束，先处理失联现场，不要据此重跑（沙僧 2026-10-18，dev.099 并入）。
   - **验收只做一轮**：交付前合一次 main、跑完相关专项即可交。之后 main 又前进时，只要没冲突、新提交没碰本车道文件、切片、转换器或探针，就不再合 main、不重跑验收，也不排队等「最新 main」；合并后总装按影响面选测、每天一次全量（三级试行，见[进度审查与验证](进度审查与验证.md)「三级检查」）；查出某条车道的问题时，总装能当场小修就修（写进变更记录），否则退回该车道返工（`合并车道.sh` 可退回本批未推送的合并）。返工只改代码或测试、没碰切片／转换器／探针时，不重跑同步（指纹仍有效），只跑相关专项（本阶段串行验收在 main 前进时整队重来、返工一轮就重同步加全量，白费数小时）。
   - **偶发失败**：并行测试对少数失败的测试会单独重跑一次，单跑通过打 ⚠「偶发」仍算通过，写进交付单；同一测试第二次偶发就修测试（固定随机、等空闲），不靠重跑。首次与重跑的输出、退出码、耗时分别保留（`<场景>.log`／`<场景>.rerun1.log`，`test_timings.json` 的 attempts），每次偶发追加到 `.git/xiyou_test_state/flaky.jsonl`，输出里打出该场景累计偶发次数，据此判断是不是第二次。单场景用时过半上限（300 秒）时按场景拆分，如 `xiyou_rules` 每难度四份、`xiyou_smart_ai` 分四份，断言总数不变。提交信息照常带 `执行者`、`核查` 两行。
4. 合并（总装，`main` 工作区要干净；合并动作一条一条做，检查可以几条攒一次）：`git merge --no-ff <分支>`；分支改了切片、转换器或参照探针时，先在 `main` 跑 `同步正式西游.py`（转换产物不入 Git，`main` 要自己重新生成；测量变化应只有车道报告的新增用例）；把交付单并入变更记录（执行者照交付单写）、交接板（待交叉核查、下一步、车道表删行）、进度账与 `当前状态.json`，删掉交付单；改动了 `01_Godot工程` 的游戏内容（`tests/` 除外）时 `开发编号.py bump "说明"` 并替换开发编号占位（只改文档、工具的合并不递增）；跑 `检查.sh --oracle`；提交「合并 <分支>（dev.NNN）」；把 `main` 推到 GitHub（用户 2026-10-18，见 AGENTS.md「底线规则」）。用 `合并车道.sh` 时：冲突解决后 `git add` 再跑同一命令接续；合并时顺带改的规则或要删的另一张交付单用 `--finish --also <路径>`（见 `07_开发环境/合并提速工具.md`）。最后 `清理工作树.sh <任务名>` 删除 worktree 与分支（车道交付后已在同一工作树换分支接着做时，`合并车道.sh` 只跳过它的工作树、照删交付分支）。**几条车道同时可合时只检查一次**（用户 2026-10-20 同意）：前几条照常准备、登记，收尾用 `合并车道.sh <任务> --finish --batch`（提交收尾，但不跑检查、不清理、不推送），最后一条不加 `--batch` 的 `--finish` 统一跑一次 `检查.sh --oracle`，通过后清理本批全部工作树并推送；白天按影响面选测时最后一条用 `--finish --affected`（见[进度审查与验证](进度审查与验证.md)「三级检查」）；最后的检查失败时本批收尾提交不推送、工作树都保留，工具列出每条车道的合并提交和带进来的文件；在嫌疑车道自己的工作树单独跑失败的场景定位。只是偶发或环境问题就修好后重跑同一命令；要撤出某条就 `合并车道.sh --abort-batch`（先把当前 main 连同未提交的登记存成 `refs/lane-merge/aborted-*` 备份，再退回本批开始前的 main，工作树都不动；已推送的批不能退），然后把没问题的车道重新合，撤出的那条修好再交付。
**及时清理（用户 2026-10-23）**：临时文件与已完成的工作树残留要及时删。合并通过后工具清掉车道工作树时，工作树里的 `04_验证/本地结果/` 临时输出一起删（不再移回主工作区）；总装合并后删掉自己的长任务日志（如 `.git/tangseng*/`）与废弃的工作树；车道交代写上「收工前删掉本车道产生的临时输出，交付单写一句已清理」。保留例外：交接板写明「不要删」的工作树（如沙僧 `state-effects-2b` 的原版证据）。
5. 中断：车道会话中断时，worktree 与分支都在，车道表写着路径；接手者进入该 worktree，照 AGENTS.md「开工」第 2 条处理现场。总装中断时，下一个会话先看车道表与 `git worktree list`，接任总装。
6. 进度审查：进度账到审查点（见[进度审查与验证](进度审查与验证.md)：50%、75%、95%）时，总装停止派新车道，等在跑的车道合并完再审查。

交叉核查照旧：车道的提交和总装的合并提交都进「待交叉核查」，由另一位执行者核查。
