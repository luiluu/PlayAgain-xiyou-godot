## 多会话并行（Orca 三方协作）

只开一个会话时不需要本节，照 [AGENTS.md](../../AGENTS.md)「开工与收工」做。同时开多个会话（cc、gpt、小A）时：

**角色与名册**（详见[天启篇三方协作](天启篇三方协作.md)，旧唐僧／悟空／八戒／沙僧等重制期代号已停用）
- **cc**（Claude Max）：**总装**（主工作区 `main`，唯一合并 `main`、推 GitHub、分配开发编号、维护交接板和变更记录、出包与补丁）＋**主力实现车道**（分支 `cc/<任务>`）。
- **gpt**（ChatGPT Plus）：**甲档交叉核查**、**美术出图**、**架构提案评审**（分支 `gpt/<任务>`）。
- **小A**（Antigravity Pro）：**第二执行轨**（界面、数据表、文案、楼层内容、美术接入、工具清理，分支 `xa/<任务>`）、**全库调研盘点**、**乙丙档交叉核查**、**总装额度接力**。

**流程**（总装部分；车道开工、交付、中断在[车道须知](车道须知.md)）
1. 派任务（总装，在 Orca 里）：在交接板「车道」表登记任务与独占文件，使用 Orca 创建工作树或派发 worker（`orca worktree create --name <任务名> --no-parent --agent <claude|codex|antigravity> --prompt "<交代>" --json` 或 `orca orchestration worker-start`）。工作树统一由 Orca 管理在 `~/orca/workspaces/再刷项目资料库/` 下，**不再在 `.claude/worktrees/` 新建工作树**。车道开工跑 `03_再刷重制_Godot/07_开发环境/新建工作树.sh --补齐 <worktree路径> --branch <cc|gpt|xa>/<任务名>` 补上引擎链接、转换产物与导入缓存。
   - **交代先算收益、分期、写停手条件**（用户 2026-10-21，起因：扩角色同步提速交沙僧时角色只剩一两批，沙僧把大半时间花在最难又几乎用不上的「按单元复用」原型上，可交的部分反而没先交）：① 派之前先算收益还剩多少（这项工作以后还会被用几次、离做完还有多远），收益快到头的不派或砍范围；② 交代按「先交可合并的一小期、再做下一期」写，每期单独验收，难的尾巴放最后并写明可以砍；③ 写清什么情况下停手回报（如做到某一步还看不到收益、要等别的车道）。给沙僧和 cc 车道的交代都照此写。
4. 合并（总装，`main` 工作区要干净；合并动作一条一条做，检查可以几条攒一次）：`git merge --no-ff <分支>`；分支改了切片、转换器或参照探针时，先在 `main` 跑 `同步正式西游.py`（转换产物不入 Git，`main` 要自己重新生成；测量变化应只有车道报告的新增用例）；把交付单并入变更记录（执行者照交付单写）、交接板（待交叉核查、下一步、车道表删行）、进度账与 `当前状态.json`，删掉交付单；改动了 `01_Godot工程` 的游戏内容（`tests/` 除外）时 `开发编号.py bump "说明"` 并替换开发编号占位（只改文档、工具的合并不递增）；跑 `检查.sh --oracle`；提交「合并 <分支>（dev.NNN）」；把 `main` 推到 GitHub（用户 2026-10-18，见 AGENTS.md「底线规则」）。用 `合并车道.sh` 时：冲突解决后 `git add` 再跑同一命令接续（接续前工具会拒带冲突标记的暂存文件）；合并提交后工具自动做快速解析检查（同名 func＋godot 加载，约半分钟），不过就停在准备阶段，改好留成未提交、重跑同一命令加 `--also <改过的文件>`，工具把修正并进合并提交（合并进行中守卫不收手动 commit／amend，tools29；`--no-parse-check` 只在卡住或确认误报时用）；单条合并要撤出用 `合并车道.sh <任务> --abort`（不要手动 `git reset`，否则同步产物与基线不跟着退）；main 有别人的未入 Git 临时文件挡合并时写进本地 `.git/info/exclude`，不挪不删；合并时顺带改的规则或要删的另一张交付单用 `--finish --also <路径>`（见 `07_开发环境/合并提速工具.md`）。最后 `清理工作树.sh <任务名>` 删除 worktree 与分支（车道交付后已在同一工作树换分支接着做时，`合并车道.sh` 只跳过它的工作树、照删交付分支）。**几条车道同时可合时只检查一次**（用户 2026-10-20 同意）：前几条照常准备、登记，收尾用 `合并车道.sh <任务> --finish --batch`（提交收尾，但不跑检查、不清理、不推送），最后一条不加 `--batch` 的 `--finish` 统一跑一次 `检查.sh --oracle`，通过后清理本批全部工作树并推送；白天按影响面选测时最后一条用 `--finish --affected`（见[进度审查与验证](进度审查与验证.md)「三级检查」）；最后的检查失败时本批收尾提交不推送、工作树都保留，工具列出每条车道的合并提交和带进来的文件；在嫌疑车道自己的工作树单独跑失败的场景定位。只是偶发或环境问题就修好后重跑同一命令；要撤出某条就 `合并车道.sh --abort-batch`（先把当前 main 连同未提交的登记存成 `refs/lane-merge/aborted-*` 备份，再退回本批开始前的 main，工作树都不动；已推送的批不能退），然后把没问题的车道重新合，撤出的那条修好再交付。
**排队顺序：快慢分道（Kyo 2026-11-11，合并瓶颈提案）**：合并动作本身每条只要几十秒到几分钟，车道等的时间来自总装不在岗、一条慢车道堵住全队、交付单格式返工（11-08～11-10 三十条合并的实测，数字在变更记录 2026-11-11「合并提速」条）。所以：
- **起队列前先看板**：总装开工、每轮起 `--queue` 之前、哨兵巡检时，先跑 `python3 03_再刷重制_Godot/07_开发环境/待合.py`（云端线程的分支只在 github 上时加 `--fetch`）。它只读，列出所有交了还没进 main 的车道（不管在不在派单里）、各等了多久、自检过没过、快还是慢、彼此冲不冲突，并打印可直接用的 `--queue` 写法。待合队列以它为准，不再只靠接续笔记手记（11-08 交付的开场声明屏不在派单里，等了两天）。`待合.py --check` 在有车道等过 4 小时时退出 1，可接进定时巡检。
- **快车道先合先推**：不动切片、转换器、参照探针、不带接受单的车道（看板「分道＝快」）合并不用同步，攒成一批 `--queue … --affected --cloud` 先合先推，不等慢车道。
- **慢车道单独一批、放队尾或夜里**：合并要同步的车道另起一条 `--queue`，不和快车道排进同一条（同一条里前面的同步没跑完，后面的都陪着等：11-09 interp8 的探针整份重跑 270 分钟，后面四条等了一夜）。预计同步超过 30 分钟的，先把手头的快车道合完推完再起。
- **自检没过的不排**：看板「退回车道」里的，把问题原文转给车道改（多数是交付单格式，车道一两分钟能改），不由总装在 main 上代改、也不用 plumbing 改车道分支（11-10 总装补过三笔，补完那棵工作树显示有改动，合并又停一次）。
- **车道之间冲突，后交付的退回**：看板按建议顺序往上叠着试合并；单独合 main 没冲突、叠在前面车道之后有冲突的那条，先合前面的，让它 `git merge main` 解掉再交付。几行的小冲突总装当场能解的照旧可以解。
- 回退：不想用看板就照旧手排，`合并车道.py` 不依赖这两个工具。

**及时清理（用户 2026-10-23）**：临时文件与已完成的工作树残留要及时删。合并通过后工具清掉车道工作树时，工作树里的 `04_验证/本地结果/` 临时输出一起删（不再移回主工作区）；总装合并后删掉自己的长任务日志（如 `.git/tangseng*/`）与废弃的工作树；车道交代写上「收工前删掉本车道产生的临时输出，交付单写一句已清理」。保留例外：交接板写明「不要删」的工作树（如沙僧 `state-effects-2b` 的原版证据）。
6. 进度审查：进度账到审查点（见[进度审查与验证](进度审查与验证.md)：50%、75%、95%）时，总装停止派新车道，等在跑的车道合并完再审查。

交叉核查照旧：车道的提交和总装的合并提交都进「待交叉核查」，由另一位执行者核查。
