## 二、Orca 工作树、分支与派活流程

1. **工作树管理**：
   - 每条车道对应一个 **Orca worktree**，统一由 Orca 管理在 `~/orca/workspaces/再刷项目资料库/` 下，**不再在 `.claude/worktrees/` 新建工作树**。
   - 新建车道可通过 Orca UI 或 CLI 创建：
     ```bash
     orca worktree create --name <任务名> --no-parent --agent <claude|codex|antigravity> --prompt "<派单交代>" --json
     ```
     或在已有工作树内通过 `orca orchestration worker-start` 派发受监督的子任务。
   - 新工作树检出后，运行 `03_再刷重制_Godot/07_开发环境/新建工作树.sh --补齐 <worktree路径> --branch <cc|gpt|xa>/<任务名>` 补齐引擎链接、转换产物与 `.godot` 导入缓存。
   - **派活必配模型和思考强度**（Kyo 2026-11-14，与 [AGENTS.md](../../AGENTS.md)「角色」节同一条）：每次派车道／worker（`orca orchestration worker-start`、开会话、子代理）都**显式写模型和思考强度**，不继承派活方自己的档位：机械活（扩数据、文案、清理、文档、乙丙档抽核，职级 P6）Sonnet＋medium，派小A／小o 时强度同样降一档（乙丙档抽核只核 P6 执行的批，见第一节「职位与职级」规则 2）；复杂系统（战斗核心、存档、天启篇新机制接线、甲档核查）Opus＋medium；架构设计、疑难排查才用 high。派单里写一句「本单配 X＋Y，因为……」。写法：
     ```bash
     orca orchestration worker-start --spec "<派单>" --agent claude --model claude-sonnet-5-5 --effort medium   # 机械活
     orca orchestration worker-start --spec "<派单>" --agent claude --model claude-opus-5-5 --effort medium     # 复杂系统、甲档核查
     ```
     `--effort` 必须带 `--model`（单写 `--effort` 会被拒）；不能和 `--terminal` 同用。小o（codex）默认模型 `gpt-6.2-sol`＋high；小A（antigravity）默认就是 Gemini 4 Hydrogen，不传 `--model`（`--model hydrogen` 会报 Unknown model ID），要 Carbon 时传 `--model gemini-4-carbon-high`，要 Neon 时传 `--model gemini-4-neon-high`，档位在派单里写明。
2. **分支与交付单命名**：

| 执行者 | 分支前缀 | 提交尾注 `执行者:` | 交付单路径 |
| --- | --- | --- | --- |
| **cc** | `cc/<任务>` | `执行者: cc`（或 `cc（<角色>）`） | `00_项目管理/交付/cc_<任务>.md` |
| **小o** | `gpt/<任务>` | `执行者: co`（工具不认「小o」） | `00_项目管理/交付/gpt_<任务>.md` |
| **小A** | `xa/<任务>` | `执行者: 小A`（ag、xa 也认） | `00_项目管理/交付/xa_<任务>.md` |

   - 提交信息末尾统一固定两行：`执行者: cc|co|小A` 与 `核查: 待审查`。
   - 文档中的开发编号统一写占位符，由总装合并时替换为实际 `dev.NNN`。
3. **并发上限与测试**：
   - 本机同时运行写代码的车道上限为 **4 条**（受 Mac 内存与测试槽限制）：建议 `cc` 最多 2 条＋总装、`小A` 最多 2 条、`小o` 最多 1 条。
   - 重测试一律走云端 `--cloud`（仓库公开，使用 GitHub Actions 免费额度）。
4. **交付与即合即删**：
   - 车道只改分配给自己的独占文件，**不改共用文件**（`交接板.md`、`变更记录.md`、`开发编号.json`、`AGENTS.md`、`00_项目管理/规则/*`）；需登记的内容一律写进交付单。
   - 车道跑完专项测试与 `交付自检.py` 后，提交交付单并通过 `orca orchestration` 回报总装。
   - 总装使用 `合并车道.py` 合并并推送 GitHub，**合并通过后立即删除该车道的工作树与分支**（`orca worktree rm` / `清理工作树.sh`），绝不堆积工作树。

1. **命名分三块**（Orca 工作区显示名）：
   - `cc·总装｜<当前合并内容>`（主工作区）
   - `cc｜<任务>·<状态>`（cc 车道）
   - `小o｜<任务或当前核查对象>`
   - `小A｜<任务>·<状态>`
   - 状态词只用：**返修中**／**等核**（或写明「等小A核」）／**已核待合**／**已合**；同时设看板状态 `in-progress`（做、返修）／`in-review`（等核、待合）／`completed`（已合）。
2. **谁改、何时改**：项目经理cc 在派单、交付、转核查、合并后各更新一次：
   ```bash
   orca worktree set --worktree path:<路径> --display-name "cc｜教派包乙·等小A核" --workspace-status in-review --comment "<备注>"
   ```
   新车道 `orca orchestration worker-start` 时直接带 `--display-name`。
3. **完成即清**：已并入 `main` 且无未提交改动的工作树，先 `orca orchestration worker-release --dispatch <dispatch_id>` 释放会话，再 `orca worktree rm --worktree path:<路径> --delete-branch`（或 `03_再刷重制_Godot/07_开发环境/清理工作树.sh <路径>`）。总装合并中的那棵由合并工具删；有活动会话删不掉的，总装列给项目经理cc 释放。
