## 二、Orca 工作树、分支与派活流程

1. **工作树管理**：
   - 每条车道对应一个 **Orca worktree**，统一由 Orca 管理在 `~/orca/workspaces/再刷项目资料库/` 下，**不再在 `.claude/worktrees/` 新建工作树**。
   - 新建车道可通过 Orca UI 或 CLI 创建：
     ```bash
     orca worktree create --name <任务名> --no-parent --agent <claude|codex|antigravity> --prompt "<派单交代>" --json
     ```
     或在已有工作树内通过 `orca orchestration worker-start` 派发受监督的子任务。
   - 新工作树检出后，运行 `03_再刷重制_Godot/07_开发环境/新建工作树.sh --补齐 <worktree路径> --branch <cc|gpt|xa>/<任务名>` 补齐引擎链接、转换产物与 `.godot` 导入缓存。
2. **分支与交付单命名**：

| 执行者 | 分支前缀 | 提交尾注 `执行者:` | 交付单路径 |
| --- | --- | --- | --- |
| **cc** | `cc/<任务>` | `执行者: cc`（或 `cc（<角色>）`） | `00_项目管理/交付/cc_<任务>.md` |
| **gpt** | `gpt/<任务>` | `执行者: gpt` | `00_项目管理/交付/gpt_<任务>.md` |
| **小A** | `xa/<任务>` | `执行者: 小A` | `00_项目管理/交付/xa_<任务>.md` |

   - 提交信息末尾统一固定两行：`执行者: cc|gpt|小A` 与 `核查: 待审查`。
   - 文档中的开发编号统一写占位符，由总装合并时替换为实际 `dev.NNN`。
3. **并发上限与测试**：
   - 本机同时运行写代码的车道上限为 **4 条**（受 Mac 内存与测试槽限制）：建议 `cc` 最多 2 条＋总装、`小A` 最多 2 条、`gpt` 最多 1 条。
   - 重测试一律走云端 `--cloud`（仓库公开，使用 GitHub Actions 免费额度）。
4. **交付与即合即删**：
   - 车道只改分配给自己的独占文件，**不改共用文件**（`交接板.md`、`变更记录.md`、`开发编号.json`、`AGENTS.md`、`00_项目管理/规则/*`）；需登记的内容一律写进交付单。
   - 车道跑完专项测试与 `交付自检.py` 后，提交交付单并通过 `orca orchestration` 回报总装。
   - 总装使用 `合并车道.py` 合并并推送 GitHub，**合并通过后立即删除该车道的工作树与分支**（`orca worktree rm` / `清理工作树.sh`），绝不堆积工作树。

## 三、天启篇验收与交叉核查（精简版）

1. **以设计稿为准验收**：
   - 天启篇无 RPGMV 原版可对照，**验收一律以 `xiyou-design-docs/重制设定/` 对应设计稿为准**。
   - 派单写清「对应设计稿哪一节、哪几条」；交付单逐条列出对应的「专项测试场景名或截图证据」，未对应的条目视为未完成。
   - 只有修改「从原版移植的共用底层逻辑」（战斗公式、原版事件、存档）时，才加跑 `--oracle` 原版对照。
2. **跨模型核查矩阵**（执行者不核查自己的提交）：

| 档位 | 范围 | 核查规则与分工 |
| --- | --- | --- |
| **甲档** | 战斗核心、存档、发行与补丁 | **合并前或合并当批必由另一家模型全量核查**：<br>• `cc` 写的 → 交 **gpt** 核查；<br>• `gpt` 或 `小A` 写的 → 交 **cc** 核查。 |
| **乙档** | 楼层内容、界面、数据表、文案、美术接入 | **每批抽核 1/5**，由非执行方（优先 **小A** 或 **cc**）抽核。 |
| **丙档** | 工具脚本、清理、文档 | **只看结论与自检输出**，不单独排人工细核。 |

3. **轻量化记录（不再一核一报告）**：
   - 取消重制期「每次核查单独立一份 `核查报告_*.md`」的做法。
   - 核查通过直接在变更记录登记销账；发现问题直接记入交接板**「待修」表**（一行一条：`分支/提交 | 档位 | 问题描述 | 负责车道`），仅 **P1 严重问题**才单独写分析报告。
   - 阶段审查改为**每个天启篇里程碑**做一次。

## 四、额度调度与接力

1. **日常调度**：
   - **cc（Max）**：承担总装及战斗核心、复杂机制实现。
   - **gpt（Plus 20 刀）**：只派高价值刀刃任务（甲档核查、美术出图、关键架构提案评审）。派单必须写清具体提交号或文件路径，不让它全库盲搜。
   - **小A（Pro）**：承担大吞吐量的代码调研、日志分析、全库盘点、界面与数据表实现、乙丙档核查。
2. **总装接力**：
   - 当 `cc` 的 5 小时额度达到 **95%** 时：手头工作以 `WIP:` 提交保存，在交接板写清当前现场，由 **小A 接力总装**（用 `待合.py` 看板合并快车道、维护交接板）；`cc` 额度恢复后交还总装。
3. **长任务不轮询**：
   - 预计超过 30 分钟的长任务一律用 `长任务.py start` 后台脱离运行并结束当前轮次，靠退出通知或定时唤醒检查结果，严禁前台空转轮询消耗三方额度。
