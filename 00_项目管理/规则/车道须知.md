# 车道须知

车道会话（cc、gpt、小A 的各条车道）开工只读本篇、[AGENTS.md](../../AGENTS.md)、[天启篇三方协作](天启篇三方协作.md) 和派活交代，**不用读整份交接板**（交代已写全；要看自己那一行或「当前状态」时只读那几行）。总装与合并流程在[多会话并行](多会话并行.md)。

## 车道是什么

- **车道**（同时最多 4 条写代码的：建议 cc 最多 2 条＋总装、小A 最多 2 条、gpt 最多 1 条；重测试一律走 `--cloud`）：每条对应一个 **Orca worktree**（位于 `~/orca/workspaces/再刷项目资料库/` 下，不再放 `.claude/worktrees`）和分支 `cc/<任务>`、`gpt/<任务>` 或 `xa/<任务>`，只改派给自己的独占文件。
- 提交信息的执行者行统一写成 `执行者: cc`、`执行者: gpt`、`执行者: 小A`（第二行 `核查: 待审查`）；交付单文件名对应 `cc_<任务>.md`、`gpt_<任务>.md`、`xa_<任务>.md`（旧写法 `claude/`、`codex/` 工具仍兼容识别）。

## 车道按文件划分（派任务时在车道表写明独占文件）

- A 内容／楼层：`03_转换工具/xiyou_slice.json`、转换器、事件解释器与脚本翻译、事件对照 baseline、敌群事件。**只能有一条**，因为这几处每层都要改。
- B 界面：界面页面（`scenes/` 下各页）、设置页、`ui_reference`。
- C 规则／机制：战斗逻辑、`mv_oracle` 探针、数值链（严格级对照）。C 和 A 都会碰战斗逻辑与探针，同时开时先在车道表里把文件划清。
- **同步排队（2026-10-25，四车道时本机 M1 Pro 8 核满载）**：同步里的 node 探针和 Godot 导入都占测试的跨工作树共用槽（`event_probe` 吃内存，占 3 槽），`检查.sh`、`新建工作树.sh --补齐` 的导入也占槽，机器上的重进程合起来不超共用上限；池满时排队，每分钟打一行「等槽」，长任务看门狗不会把排队判成卡死（2026-10-25 哪吒，见 `07_开发环境/长任务与增量同步.md`）。转换器本身不占槽，所以启动 `同步正式西游.py` 前仍先 `pgrep -fl 同步正式西游.py`，有别的同步在跑就先做别的；专项因 600 秒超时失败先看负载、重跑一次再下结论。
- **原沙僧独占的核心文件放开（用户 2026-10-27）**：`battle_logic.gd`、`actor.gd`、`battler.gd`、`damage.gd`、`xstate.gd` 等原归 Codex 的文件，现在 cc 车道可以改（不再需要总装批单行例外）；交付单「待交叉核查」里逐个列出改了哪些这类文件，请沙僧重点核。同一时间仍只给一条车道改同一个文件。
- 首选 A＋B 并行；共用的公共组件只由一条车道改，另一条要用时等它合并。

## 共用文件只由总装改

- 共用文件：交接板、变更记录、重制步骤清单、`当前状态.json`、`来源登记.json`、开发编号（`开发编号.json`、`project.godot`、`build_info.json`）。车道要写进这些文件的内容，写进 **交付单** `00_项目管理/交付/<分支名把 / 换成 _>.md`（模板见[该目录 README](../交付/README.md)）；每个分支单独一个文件，合并时不会冲突。
- 编号：优化登记 O-NNN 由总装派任务时在车道表预分配，车道只用分给自己的号。开发编号在合并时才确定，车道在文档里写开发编号占位，总装合并时换成实际编号（占位写法只写在 [AGENTS.md「底线规则」](../../AGENTS.md)，因为合并工具会替换车道改过的文件里的占位；`main` 上的 `检查.sh` 会报出遗留的占位与未并入的交付单）。
- 在 worktree 里运行 `同步正式西游.py` 时自动不写来源登记／当前状态；正式源的登记只在 `main` 上做。

## 开工、过程、交付、中断

- **开工**：读派活交代、本篇与 AGENTS.md；在 app 给的工作树里跑一条 `03_再刷重制_Godot/07_开发环境/新建工作树.sh --补齐 <自己的路径> --branch <派单的分支，如 cc/nezha-tools22> [--from <提交或分支>]`：先从 `--from`（默认 `main`）切出派单的分支（app 建的 `cc/<随机名>` 留着不删；工作树有已跟踪的未提交改动、或该分支已存在时它拒绝），再补齐引擎、产物与导入缓存（tools22）；派单指定的旧工作树不要去写，守卫不许；交接板不用整份读，要看车道表自己那一行或「当前状态」就只读那几行（只读）；`git status`、`git log` 照常看。开工后先 `git merge main`（分支从旧提交切出时，补齐后的同步会把 main 新增的角色等报成「删除」白跑一轮；`--补齐` 发现分支落后 main 且 main 改了切片／转换器／探针时会提示，tools33）。中途照常小步提交、`WIP:` 提交到自己的分支；过程中只跑相关专项。车道只在自己的线程里说话：项目聊天或别的线程里的问题不是问自己的，不去回答，除非唐僧转来（八戒_30 2026-10-20：车道读到项目聊天里的问题会偏题回答）。
- **交付**：先 `git merge main` 并解决冲突；合并进来的提交改了切片、转换器或探针时，再跑一次 `新建工作树.sh --补齐 <路径>` 让转换产物跟上（转换产物不入 Git）；扩了切片或改了探针的，最后在工作树跑一次 `同步正式西游.py --accept-additions`（留下产物指纹，总装合并时可免重跑；同步结束自动 `godot --import`）；改了切片的再跑 `03_转换工具/内容覆盖检查.py`，看过报告再 `--update-baseline`；交 Godot 改动前先跑一次 `python3 07_开发环境/语法检查.py`（约 10 秒、不占测试槽，总装八 10-31 据哪吒 tools27 加）；新加的断言想确认真咬得住，用 `07_开发环境/反向验证.py <清单.json>`（清单列「文件＋要改的片段→改成什么」，逐项改→单跑专项→记失败数→用备份字节还原，不用 git checkout，最后打表；`--dry-run` 只查清单能不能定位，tools33）；并行测试的名字默认只按**全名**匹配（`xiyou_rules` 只选它自己一个），要前缀显式写 `前缀*`（`xiyou_rules*`）；不带 `*` 的名字只有前缀能匹配时会提示、不选（tools38；`XIYOU_BARE_PREFIX=1` 回到旧的按前缀，旧模式下扩出 40 个以上先停下，`--wide` 放行）；改函数签名前 `rg` 全工程（含 tests 里的覆写）。**车道不跑全量 `检查.sh`**（用户 2026-10-21：总装合并后统一跑一次就够，车道在 worktree 里全量约 30 分钟、与总装重复）：只跑与改动相关的专项＋必跑项（**手写选测名单前先跑 `python3 03_再刷重制_Godot/07_开发环境/选测.py main --list`**：它按 `选测对照.json` 打印你的改动相对 main 会选中的场景，一行一个、可直接接到 `并行测试.py` 后面；你的名单至少包含它列出的战斗核心类场景（如 `xiyou_determinism`），不跑的写进交付单并说明为什么——drops1 改了 battle_logic 掉落却漏了 xiyou_determinism，总装收尾才挂，tools35）；`并行测试.py <godot> <工程> 场景全名或前缀*…`；不给 `--log-dir` 时日志自动写到 `04_验证/本地结果/并行测试/<时间戳>/`，失败项打印完整日志路径，管道给 `tail` 时加 `--quiet`；写探针或临时 node 检查脚本结尾要 `process.exit`，见 `mv_oracle/README.md`；改了谁就跑谁和直接依赖它的测试；必跑项见[进度审查与验证](进度审查与验证.md)「三级检查」，列进交付单「验证」），写好交付单最后写「可合并」，提交。**扩角色车道（悟空，用户 2026-10-20）**：同步前先只跑角色相关专项（`slice_probe`（只量新角色：`XIYOU_PROBE_ACTORS=新角色号,… node slice_probe.cjs <难度>`，六难度可各开一个进程并行，每个难度量完即写 `.sandbox/slice_actors/`，不进同步；不带参数整份单跑要 35 分钟以上，tools47）／`actor_passive_probe` 单探针、`xiyou_actor_p0`、`xiyou_rules*` 中含新角色的难度段、`xiyou_wtype`），有问题当场改，做不了的角色先剔出并写进交付单，最后只跑一轮同步，不做「查出问题→重同步→再查」的重复轮次。长任务（同步、`检查.sh`）用 `python3 07_开发环境/长任务.py start <日志> -- <命令>` 启动：它在新会话里跑，会话空闲被停（Remote Control）也不会带停；然后在前台反复跑 `07_开发环境/等待任务.sh <日志> --timeout 540`（每次在 Bash 十分钟上限内返回，124＝还在跑，接着再等），不靠后台任务通知唤醒（曾因通知没来空转一小时）；会话连续一小时没有新消息会被 Remote Control 停掉、连带停掉后台任务（11-05 platform1 收尾的本机选测就这样被掐），所以任何等待（云端、别的车道）都别空等超过 50 分钟，用前台循环或定时约 50 分钟回来看一次（协调 11-05）；返回 2 且状态 orphaned 表示旧任务无法确认已结束，先处理失联现场，不要据此重跑（沙僧 2026-10-18，dev.099 并入）。
   - **工具快速回归必跑**（tools65，唐僧派单、哪吒 2026-11-05）：交付前（改的不只是文档）再跑一次 `python3 03_再刷重制_Godot/07_开发环境/工具回归.py`（几十秒，并行 3 项）：它包含 `测试选测.py CheckerTests`（`检查.sh` 的替身名单现在自动从 `检查.sh` 解析，你给 `检查.sh` 加新检查不用再手改名单）、`测试插件备注覆盖.py`（已知例绑定了被你做掉的备注标签就会挂，同一提交里改测试的已知例）、`测试状态js翻译.py`（同理，绑定了被你翻掉的状态）等；改到 `检查.sh`、`选测对照.json`、转换器清单、翻译、插件备注时尤其要跑。`选测.py main --list` 在非文档改动时也会提醒这一条。总装 `合并车道.sh --finish --affected` 在开云端选测前会先跑它，没过就早停（`XIYOU_TOOL_GATE=0` 可关），所以车道这里漏了也只是在合并时早一步被挡住、不再白耗云端。单跑某一类：`python3 测试选测.py CheckerTests`（可点名多个类／用例）。
   - **交付自检必跑**（Kyo 2026-11-11，合并瓶颈提案）：交付单写好、标「可合并」、**提交之后**，在自己的工作树跑 `python3 03_再刷重制_Godot/07_开发环境/交付自检.py`（几秒到十几秒，只读，不改任何文件）。它在临时库里照搬总装 `合并车道.py` 准备阶段的检查（交付单只有一份、状态行、变更记录草稿、优化登记草稿是不是 8 列表格、优化号占位对不对得上、删没删基线参照用例），再对当前 main 真的试合并一次（冲突、合并后同名 func、await 三元式、冲突标记），并查工作树有没有没提交的东西；慢车道另查同步指纹和接受单条数。退出码 0 才回报「可合并」；有问题照它列的逐条改、提交、重跑。它只看已提交的内容，所以先提交再跑。输出里的「分道」写明本车道是快车道还是慢车道，回报总装时带上这一句。11-09～11-10 两条合并队列各重起 5 次全是这类格式问题，每次都要等总装回来才有人修。查别的分支用 `--branch <分支>`；云端容器是浅克隆也能跑（基准自动取 `origin/main`）。
   - **慢车道带着产物交付**（同上）：改了切片、转换器、参照探针或带接受单的车道，合并时 main 要跑同步；交付前在本树把同步跑完（上面「交付」一段已有），留下同步指纹，测量有改变的把接受单生成好、逐条补理由、一起提交。自检发现没有指纹、指纹过期、缺接受单或条数不够都算问题。没有原版与转换产物的云端车道做不了这一步，自检只提示，总装按慢车道排到队尾。
   - **验收只做一轮**：交付前合一次 main、跑完相关专项即可交。之后 main 又前进时，只要没冲突、新提交没碰本车道文件、切片、转换器或探针，就不再合 main、不重跑验收，也不排队等「最新 main」；合并后总装按影响面选测、每天一次全量（三级试行，见[进度审查与验证](进度审查与验证.md)「三级检查」）；查出某条车道的问题时，总装能当场小修就修（写进变更记录），否则退回该车道返工（`合并车道.sh` 可退回本批未推送的合并）。返工只改代码或测试、没碰切片／转换器／探针时，不重跑同步（指纹仍有效），只跑相关专项（本阶段串行验收在 main 前进时整队重来、返工一轮就重同步加全量，白费数小时）。
   - **偶发失败**：并行测试对少数失败的测试会单独重跑一次，单跑通过打 ⚠「偶发」仍算通过，写进交付单；同一测试第二次偶发就修测试（固定随机、等空闲），不靠重跑。首次与重跑的输出、退出码、耗时分别保留（`<场景>.log`／`<场景>.rerun1.log`，`test_timings.json` 的 attempts），每次偶发追加到 `.git/xiyou_test_state/flaky.jsonl`，输出里打出该场景累计偶发次数，据此判断是不是第二次。单场景用时过半上限（300 秒）时按场景拆分，如 `xiyou_rules` 每难度四份、`xiyou_smart_ai` 分四份，断言总数不变。提交信息照常带 `执行者`、`核查` 两行。
- **中断**：车道会话中断时，worktree 与分支都在，车道表写着路径；接手者进入该 worktree，照 AGENTS.md「开工」第 2 条处理现场。总装中断时，下一个会话先看车道表与 `git worktree list`，接任总装。
- **停了就换新会话、交接线 40%**（Kyo 2026-11-02，省额度；取代 10-31「Kyo 不在可做到 70%」）：车道上下文到 40% 就 WIP 提交、在交付单写接续要点、回报总装后停手，不管 Kyo 在不在。车道停下（额度用完、到线、交接）后不再续旧会话，由总装派新会话读交付单接着做（同一分支用 `git switch --ignore-other-worktrees <分支>` 再 `新建工作树.sh --补齐`）。派单开头写明模型和思考强度（按[会话接力与省额度](./会话接力与省额度.md)「车道模型与强度按任务难度」）。
